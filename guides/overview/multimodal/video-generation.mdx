## How It Works

Unlike text or image generation, video generation is **asynchronous** because generating video takes significantly longer. The workflow is:

1. **Submit** a generation request to `POST /api/v1/videos`
2. **Receive** a job ID and polling URL immediately
3. **Poll** the polling URL (`GET /api/v1/videos/{jobId}`) until the job reaches a terminal status: `completed`, `failed`, `cancelled` or `expired`
4. **Download** the video from the content URL (`GET /api/v1/videos/{jobId}/content`) once the status is `completed`

## API Usage

### Submitting a Video Generation Request

<CodeGroup>

```python Python expandable lines
import requests
import json
import time

url = "https://openrouter.ai/api/v1/videos"
headers = {
    "Authorization": f"Bearer {API_KEY_REF}",
    "Content-Type": "application/json"
}

payload = {
    "model": "google/veo-3.1",
    "prompt": "A golden retriever playing fetch on a sunny beach with waves crashing in the background"
}

# Step 1: Submit the generation request
response = requests.post(url, headers=headers, json=payload)
response.raise_for_status()
result = response.json()

job_id = result["id"]
polling_url = result["polling_url"]
print(f"Job submitted: {job_id}")
print(f"Status: {result['status']}")

# Step 2: Poll until completion
while True:
    time.sleep(30)  # Wait 30 seconds between polls
    poll_response = requests.get(polling_url, headers=headers)
    poll_response.raise_for_status()
    status = poll_response.json()

    print(f"Status: {status['status']}")

    if status["status"] == "completed":
        # Step 3: Download the video
        content_url = status["unsigned_urls"][0]
        video_response = requests.get(content_url, headers=headers)
        video_response.raise_for_status()
        with open("output.mp4", "wb") as f:
            f.write(video_response.content)
        print("Video saved to output.mp4")
        break
    elif status["status"] in ("failed", "cancelled", "expired"):
        raise RuntimeError(f"Generation {status['status']}: {status.get('error', 'Unknown error')}")
```


### Submitting a Video Upscale Request

Send this JSON body to `POST /api/v1/videos`, replacing the example URL with your source video URL. This example uses FLUX Video Upscale. If you have access to Runway video upscale, use its model ID with the same `input_references` shape and omit `prompt`.


### Request Parameters

| Parameter | Type | Required | Description |
|---|---|---|---|
| `model` | string | Yes | The model to use for video generation (e.g., `google/veo-3.1`) |
| `prompt` | string | Yes, except for video upscale models and models that can generate from image input alone | Text description of the video to generate. Runway video upscale rejects this field |
| `duration` | integer | No | Duration of the generated video in seconds |
| `resolution` | string | No | Resolution of the output video (e.g., `720p`, `1080p`) |
| `aspect_ratio` | string | No | Aspect ratio of the output video (e.g., `16:9`, `9:16`, `3:2`) |
| `size` | string | No | Exact pixel dimensions in `WIDTHxHEIGHT` format (e.g., `1280x720`). Interchangeable with `resolution` + `aspect_ratio` |
| `frame_images` | array | No | Images for first/last frames (image-to-video) |
| `input_references` | array | For video upscaling | Reference assets for generation, such as images for style guidance. For upscaling, provide the source video as a `video_url` entry |
| `generate_audio` | boolean | No | Whether to generate audio alongside the video. When omitted, the serving endpoint's default applies (see `generate_audio` in the models endpoint), which can be `false` |
| `seed` | integer | No | Seed for deterministic generation (not guaranteed by all providers) |
| `callback_url` | string | No | URL to receive a webhook notification when the job completes. Overrides the workspace-level default callback URL if set. Must be HTTPS |
| `previous_job_id` | string | No | ID of a completed video job to edit or extend. The new job runs on the same model and endpoint as the previous one. Only models that support continuation accept it. The API checks that the job belongs to your account, not to the request's `user`, so if you share one OpenRouter account across end users, verify that the signed-in user owns the job before forwarding a client-supplied ID |
| `upscale_factor` | number | No | Upscale factor for video upscaling models only; not supported by video generation models. Upscaling models take the source video as exactly one `video_url` entry in `input_references`, and some reject fields: Runway video upscale rejects `prompt` and `upscale_factor`, so `prompt` is not required there |
| `creativity` | integer | No | Creativity level for video upscaling models only; not supported by video generation models |
| `user` | string | No | Stable identifier for your end-user, forwarded to Broadcast and private logging as the end-user ID; never sent to the provider |
| `session_id` | string | No | Unique identifier (max 256 characters) for grouping related requests in Broadcast and private logging; never sent to the provider. Overrides the `x-session-id` header if both are set. |
| `trace` | object | No | Observability and tracing metadata forwarded to configured Broadcast destinations. Named fields (`trace_id`, `trace_name`, `span_name`, `generation_name`, `parent_span_id`) are optional strings; custom keys may hold other JSON value types |
| `provider` | object | No | [Video provider routing](#provider-routing) preferences and provider-specific passthrough configuration under `options`. `data_collection` takes `allow` (default) or `deny`; `deny` excludes endpoints that train on your data, but not endpoints that retain prompts. No video endpoint currently offers Zero Data Retention, so `zdr: true` fails routing. |

### Using Images

There are two ways to provide images, each triggering a different generation mode:

- **`frame_images`**: Specifies first or last frame images for **image-to-video** generation. Each entry must include a `frame_type` of `first_frame` or `last_frame`.
- **`input_references`**: Provides style or content reference images for **reference-to-video** generation. The model uses these as visual guidance rather than exact frames.

If both fields are provided, `frame_images` takes precedence and the request is treated as image-to-video.

#### Image-to-Video (frame_images)

```json lines
{
  "model": "alibaba/wan-3.0",
  "prompt": "A character walking through a forest",
  "frame_images": [
    {
      "type": "image_url",
      "image_url": {
        "url": "https://example.com/first-frame.png"
      },
      "frame_type": "first_frame"
    }
  ],
  "resolution": "1080p"
}
```

#### Reference-to-Video (input_references)

```json lines
{
  "model": "alibaba/wan-3.0",
  "prompt": "A colossal solar flare beside a planet",
  "input_references": [
    {
      "type": "image_url",
      "image_url": {
        "url": "https://example.com/style-ref.png"
      }
    }
  ],
  "resolution": "1080p"
}
```

### Provider routing

For `POST /api/v1/videos`, set `provider.order` to prefer providers in the listed order, `provider.only` to allow only the listed provider slugs, or `provider.ignore` to skip specific providers. For example, to submit a Hailuo 3 Max job only to MiniMax:

```json
{
  "model": "minimax/hailuo-3-max",
  "prompt": "A slow camera pan across a lake at sunset",
  "provider": { "only": ["minimax"] }
}
```

Video generation does not support `provider.sort` for price, latency, or throughput. OpenRouter selects one eligible endpoint for the job and does not retry it on another provider if submission fails, so `provider.allow_fallbacks` does not apply. Use `only`, not `order`, if the job must use a specific provider.

Don't use `"only": []` to prevent a submission. If your account's allowed-providers list includes an eligible provider, OpenRouter can still submit the job to that provider. If an empty provider selection should prevent a job, don't send the request.

### Provider-Specific Options

You can pass provider-specific options using the `provider` parameter. Options are keyed by provider slug, and only the options for the matched provider are forwarded:

```json lines
{
  "model": "google/veo-3.1",
  "prompt": "A time-lapse of a flower blooming",
  "provider": {
    "options": {
      "google-vertex": {
        "parameters": {
          "personGeneration": "allow",
          "negativePrompt": "blurry, low quality"
        }
      }
    }
  }
}
```

Google Veo models are the only video models that nest options in a `parameters` object. Other video models, including other Google video models, take their allowed passthrough keys directly under the slug of the provider the request is routed to. A `parameters` object sent to them is not forwarded, and Runway video upscale rejects any provider options. For example, Seedance 2.0 is served by the Seed provider, so it takes `watermark` directly under the `seed` slug:

```json lines
{
  "model": "bytedance/seedance-2.0",
  "prompt": "A time-lapse of a flower blooming",
  "provider": {
    "options": {
      "seed": {
        "watermark": false
      }
    }
  }
}
```

A Seedance request routed to BytePlus uses the `byteplus` slug instead of `seed`.

Use the [Video Models API](#via-the-video-models-api) to check which passthrough parameters each model supports via the `allowed_passthrough_parameters` field.

## Response Format

### Submit Response (202 Accepted)

When you submit a video generation request, you receive an immediate response with the job details:

```json lines
{
  "id": "abc123",
  "polling_url": "https://openrouter.ai/api/v1/videos/abc123",
  "status": "pending"
}
```

### Poll Response

When polling the job status, the response includes additional fields as the job progresses:

```json lines
{
  "id": "abc123",
  "generation_id": "gen-1234567890-abcdef",
  "polling_url": "https://openrouter.ai/api/v1/videos/abc123",
  "status": "completed",
  "unsigned_urls": [
    "https://openrouter.ai/api/v1/videos/abc123/content?index=0"
  ],
  "usage": {
    "cost": 0.25,
    "is_byok": false
  }
}
```

### Job Statuses

| Status | Description |
|---|---|
| `pending` | The job has been submitted and is queued |
| `in_progress` | The video is being generated |
| `completed` | The video is ready to download |
| `failed` | The generation failed (check the `error` field) |
| `cancelled` | The job was cancelled before the video was ready (check the `error` field) |
| `expired` | The job ran past its time limit without finishing (check the `error` field) |

`completed`, `failed`, `cancelled` and `expired` are terminal: stop polling once the job reaches any of them.

### Downloading the Video

Once the job status is `completed`, the `unsigned_urls` array contains URLs to download the generated video content. These URLs are not presigned, so send your API key in the `Authorization` header just as you do when polling. Each entry points at the content endpoint, which you can also call directly:

```bash lines
curl "https://openrouter.ai/api/v1/videos/{jobId}/content?index=0" \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  --output video.mp4
```

The `index` query parameter defaults to `0` and can be used if the model generates multiple video outputs.

When OpenRouter holds a stored copy of the outputs, the completed response also includes `urls`: one signed download URL per output that works without an API key until `expires_at`. Use it where you cannot set headers, such as a `<video>` tag, `ffmpeg`, or a tool that only accepts a URL. Anyone holding one of these URLs can download that output until it expires, so do not log or share them. `unsigned_urls` keeps working with your API key for as long as the output is available, including when `urls` is absent.

## Webhooks

Instead of polling for job status, you can receive a webhook notification when a video generation job completes. There are two ways to configure a callback URL:

1. **Per-request**: Pass `callback_url` in the request body. This takes priority over the workspace default.
2. **Workspace default**: Set a default callback URL in your [workspace settings](/guides/features/workspaces). This applies to all video generation requests that don't specify their own `callback_url`.

### Webhook Payload

When a job reaches a terminal state, OpenRouter sends a POST request to the callback URL with an event envelope. Each delivery also carries an `X-OpenRouter-Idempotency-Key` header of the form `<job_id>-<status>` for safe retry deduplication.

`video.generation.completed`:

```json lines

  "created_at": "2026-04-24T12:00:00.000Z",
  "data": {
    "id": "abc123",
    "status": "completed",
    "generation_id": "gen-xyz789",
    "model": "google/veo-3.1",
    "unsigned_urls": [
      "https://openrouter.ai/api/v1/videos/abc123/content?index=0"
    ],
    "usage": {
      "cost": 0.5,
      "is_byok": false
    }
  }
}
```

`video.generation.failed`:

### Signing Secret

You can configure a signing secret in your [workspace settings](/guides/features/workspaces) to verify that webhook payloads are authentically from OpenRouter. When a signing secret is configured, each webhook delivery includes an `X-OpenRouter-Signature` header. Without a signing secret, deliveries are unsigned and any client can imitate them, so a receiver that expects signed webhooks must reject requests when it has no secret to verify against.

The signature includes a timestamp and an HMAC hash:

```lines
X-OpenRouter-Signature: t=1234567890,v1=a1b2c3d4...
```

### Verifying Signatures

To verify the signature on your webhook receiver:

1. Extract the timestamp (`t`) and signature hash (`v1`) from the header
2. Construct the signed payload: `{timestamp},{raw_request_body}` (joined with a comma)
3. Compute the HMAC-SHA256 of the signed payload using your signing secret as the key
4. Compare the hex-encoded result with the `v1` value

<CodeGroup>

```typescript expandable lines
import crypto from 'crypto';

const FIVE_MINUTES_IN_SECONDS = 300;

function verifyWebhookSignature(
  rawBody: string,
  signatureHeader: string,
  secret: string,
): boolean {
  // An empty secret produces an HMAC anyone can compute, so treat it as misconfiguration.
  if (!secret) {
    return false;
  }

  const parts = signatureHeader.split(',');
  const timestamp = parts.find((p) => p.startsWith('t='))?.slice(2);
  const hash = parts.find((p) => p.startsWith('v1='))?.slice(3);

  if (!timestamp || !hash) {
    return false;
  }

  // Reject timestamps older than 5 minutes to prevent replay attacks
  const age = Math.floor(Date.now() / 1000) - Number(timestamp);
  if (Number.isNaN(age) || age > FIVE_MINUTES_IN_SECONDS) {
    return false;
  }

  const signedPayload = `${timestamp},${rawBody}`;
  const expected = crypto
    .createHmac('sha256', secret)
    .update(signedPayload)
    .digest('hex');

  // The v1 value must be a 64-character hex digest. Reject anything else before
  // comparing, because timingSafeEqual throws when the byte lengths differ.
  if (!/^[0-9a-f]{64}$/.test(hash)) {
    return false;
  }

  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(hash),
  );
}

const secret = 'your_signing_secret';
const rawBody = JSON.stringify({
  type: 'video.generation.completed',
  data: { id: 'abc123', status: 'completed' },
});

  .createHmac('sha256', secret)
  .update(`${timestamp},${rawBody}`)
  .digest('hex');
const signatureHeader = `t=${timestamp},v1=${signature}`;

console.log('Valid signature:', verifyWebhookSignature(rawBody, signatureHeader, secret));
```

```python title="Python" lines
import hashlib
import hmac
import json
import time

FIVE_MINUTES_IN_SECONDS = 300


def verify_webhook_signature(raw_body: str, signature_header: str, secret: str) -> bool:
    # An empty secret produces an HMAC anyone can compute, so treat it as misconfiguration.
    if not secret:
        return False

    parts = signature_header.split(",")
    timestamp = next((p[2:] for p in parts if p.startswith("t=")), None)
    hash_ = next((p[3:] for p in parts if p.startswith("v1=")), None)

    if not timestamp or not hash_:
        return False

    # Reject timestamps older than 5 minutes to prevent replay attacks
    try:
        age = int(time.time()) - int(timestamp)
    except ValueError:
        return False
    if age > FIVE_MINUTES_IN_SECONDS:
        return False

    signed_payload = f"{timestamp},{raw_body}"
    expected = hmac.new(
        secret.encode(), signed_payload.encode(), hashlib.sha256
    ).hexdigest()

    # The v1 value must be a 64-character hex digest. Reject anything else before
    # comparing, because compare_digest raises on non-ASCII input.
    if len(hash_) != 64 or any(c not in "0123456789abcdef" for c in hash_):
        return False

    return hmac.compare_digest(expected, hash_)


# Example: verify a sample webhook delivery
secret = "your_signing_secret"
raw_body = json.dumps(
    {"type": "video.generation.completed", "data": {"id": "abc123", "status": "completed"}},
    separators=(",", ":"),
)
timestamp = int(time.time())
signature = hmac.new(
    secret.encode(), f"{timestamp},{raw_body}".encode(), hashlib.sha256
).hexdigest()
signature_header = f"t={timestamp},v1={signature}"

print("Valid signature:", str(verify_webhook_signature(raw_body, signature_header, secret)).lower())
print("Tampered body:", str(verify_webhook_signature(raw_body + " ", signature_header, secret)).lower())
```

```go title="Go" lines
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
	"time"
)

const fiveMinutesInSeconds = 300

func sign(secret, payload string) string {
	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write([]byte(payload))
	return hex.EncodeToString(mac.Sum(nil))
}

func verifyWebhookSignature(rawBody, signatureHeader, secret string) bool {
	// An empty secret produces an HMAC anyone can compute, so treat it as misconfiguration.
	if secret == "" {
		return false
	}

	var timestamp, hash string
	for _, p := range strings.Split(signatureHeader, ",") {
		if v, ok := strings.CutPrefix(p, "t="); ok && timestamp == "" {
			timestamp = v
		} else if v, ok := strings.CutPrefix(p, "v1="); ok && hash == "" {
			hash = v
		}
	}

	if timestamp == "" || hash == "" {
		return false
	}

	// Reject timestamps older than 5 minutes to prevent replay attacks
	ts, err := strconv.ParseInt(timestamp, 10, 64)
	if err != nil || time.Now().Unix()-ts > fiveMinutesInSeconds {
		return false
	}

	expected := sign(secret, timestamp+","+rawBody)

	// hmac.Equal is a constant-time comparison
	return hmac.Equal([]byte(expected), []byte(hash))
}

func main() {
	// Example: verify a sample webhook delivery
	secret := "your_signing_secret"
	rawBody := `{"type":"video.generation.completed","data":{"id":"abc123","status":"completed"}}`
	timestamp := strconv.FormatInt(time.Now().Unix(), 10)
	signature := sign(secret, timestamp+","+rawBody)
	signatureHeader := "t=" + timestamp + ",v1=" + signature

	fmt.Println("Valid signature:", verifyWebhookSignature(rawBody, signatureHeader, secret))
	fmt.Println("Tampered body:", verifyWebhookSignature(rawBody+" ", signatureHeader, secret))
}
```

## Best Practices

- **Detailed Prompts**: Provide specific, descriptive prompts for better video quality. Include details about motion, camera angles, lighting, and scene composition
- **Appropriate Resolution**: Higher resolutions take longer to generate and cost more. Choose the resolution that fits your use case
- **Polling Interval**: Use a reasonable polling interval (e.g., 30 seconds) to avoid excessive API calls. Video generation typically takes 30 seconds to several minutes depending on the model and parameters
- **Error Handling**: Treat `failed`, `cancelled` and `expired` as terminal states and handle the `error` field appropriately
- **Reference Images**: When using reference images, ensure they are high quality and relevant to the desired video output

## Zero Data Retention

Video generation is **not eligible** for [Zero Data Retention (ZDR)](/guides/features/zdr). Because video generation is asynchronous, the provider must retain the generated video output briefly so you can retrieve it after generation completes. This temporary retention is inherent to the async polling workflow, and you can't bypass it.

If you have ZDR enforcement enabled (either via [account settings](https://openrouter.ai/settings/privacy) or the per-request `zdr` parameter), OpenRouter won't route video generation requests.

## Troubleshooting

**Job stays in `pending` for a long time?**
- Video generation can take several minutes depending on the model, resolution, and server load
- Continue polling at regular intervals

**Generation failed?**
- Check the `error` field in the poll response for details
- Verify the model supports video generation (`output_modalities` includes `"video"`)
- Ensure your prompt is appropriate and within model guidelines
- Check that any reference images are accessible and in supported formats

**Model not found?**
- Use the [Video Models API](#via-the-video-models-api) or the [Models page](/guides/overview/models) to find available video generation models
- Verify the model slug is correct (e.g., `google/veo-3.1`)

**Chat Completions rejects your video model?** Submit a new request to `POST /api/v1/videos` without a `messages` array. To generate a video from text, send a top-level `prompt` as shown in the [video generation request example](#submitting-a-video-generation-request). To upscale a video, send the source video in `input_references` as shown in the [video upscale request example](#submitting-a-video-upscale-request). Runway video upscale requires one `video_url` entry and rejects `prompt`.
