# Ori product metrics

The Ori product and harness dashboards use daily successful-inference facts for activity, retention, and usage intensity. Raw CLI observations remain separate diagnostic views. A direct handoff is a launch observation; a managed invocation records its completion. Neither proves that a user finished a task.

## Collection and attribution

The public telemetry endpoint accepts optional `event_id` and numeric `schema_version` envelope fields. Older clients remain valid, and future versions remain available in ordinary telemetry logs. Product interpretation supports only the missing legacy version and version 1; other explicit versions are `projection_rejected`. After responding, supported `install_first_run` and `agent_run` observations enter `ori_product_events_v1` with server-authenticated account and key identifiers. The projection excludes arbitrary props, errors, prompts, credentials, and installer throwaway identities. Product queries interpret stored versions 0 (legacy) and 1 only.

A client event UUID identifies an observation across repeated delivery. Older events use a deterministic digest of the quantitative projection, which cannot distinguish identical legacy observations. Conflicting payloads or authenticated identities remain visible to the join guard. Events beyond 400 days of history or more than five minutes ahead of receipt time are omitted from product persistence and counted as `projection_rejected`; ordinary telemetry delivery is unaffected.

Inference uses the canonical ClickHouse generation ledger. One server-side `INSERT SELECT` stages deduplicated generation facts in `ori_product_generation_facts_v1`; work-day and model-day aggregates derive from that same snapshot. Raw generations never enter the JavaScript report payload. Shadow and server-tool records are excluded; free successful requests qualify as work. Successful work accepts chat `stop`/`length`/`tool_calls` and image/video `complete` outcomes, excluding cancelled rows. `first_request_at` includes counted failures and cancellations, and `first_paid_at` includes any counted attempt carrying known positive spend. The attempt funnel cannot see failures that never produced a ledger row.

Generation deduplication is bounded to each UTC day and assumes `generations.created_at` is immutable for a generation ID. Work/model conflicts observed in an authorized snapshot survive later source compaction. Only conflict evidence is carried forward; an absent source generation does not inherit old request or spend totals. Conflicts erased before the first authorized observation, or contradictory copies dated on different days, cannot be reconstructed by this report. Account erasure takes precedence over retaining identifying conflict evidence.

A confident bridge requires compatible authenticated key/account, installation, harness, surface, environment, and deployment associations, plus a supported session-attribution capability. Repeated run events do not multiply generation totals. Unsupported, unverified, conflicting, or missing joins remain coverage gaps. In particular, old native Ori clients and Muse cannot be assumed to propagate their declared session identifier.

Report collection captures one authorized snapshot map and one association/first-use classification before reading its fact grains. Activity, models, coverage, and exact progression reuse that classification rather than independently interpreting newly arriving telemetry. Every model child inherits its session/day parent's validity.

`generations.spend_is_known` records original billing provenance before any null-to-zero repair. New producers distinguish measured free work from absent pricing, including BYOK components; false or unknown provenance survives normalization and replay. Legacy rows and Spanner backfills without provenance remain unknown. `requests_with_spend` counts successful requests with known cost; `requests_with_billing` also includes counted failed/cancelled attempts. Timestamped generation facts retain the ledger's six-decimal precision as `Decimal(38, 6)`. Work/model-day aggregates and Datadog gauges use floating-point numbers for reporting, not exact ledger accounting.

Coverage dimensions describe the declarations: each dimension remains known only when every observation in the session agrees on its derived value. Conflicting values become `unknown`, including hosting. This preserves useful harness diagnostics for consistent unsupported or unverified declarations. Inference activity requires a valid association and exposes unknown dimensions otherwise. Blank installation identities cannot create activation cohorts.

## Definitions

- **Identity:** Account and installation views are separate. Installation activity here is the authenticated inference subset, not a count of all anonymous work. Never add account and installation uniques.
- **Populations:** Execution environment, hosting, launch surface, and harness are separate dimensions. The `external-user` first-use population excludes known internal installations; it is not proof that every remaining anonymous installation belongs to an external customer. Direct and interactive surfaces do not prove human initiation.
- **Time and version:** Every report uses completed UTC days and an exclusive midnight `report_end`. Corrected definitions use `metric_version: 2`; frozen version-1 payloads are neither edited nor reinterpreted. All account/install activity rows use `row_kind:activity`; the harness tag distinguishes the aggregate from a specific harness.
- **Activity:** Distinct identities in trailing 1, 7, and 30 days ending together. DAU/WAU and WAU/MAU use those aligned windows.
- **Returning:** Work in both the current and preceding seven-day windows. The return percentage divides by the preceding window's active population.
- **Habit:** Distinct active days per identity in seven days, median/p90 active days, and counts at one, two, three through four, and five through seven days.
- **Depth:** Median/p90 successful requests per active identity and the fraction of requests contributed by the heaviest one percent, rounded up to at least one identity. Small populations require that context when interpreting concentration.
- **Activation:** Unambiguous first-use installations in a completed cohort that produce direct or interactive successful inference within seven days. An identified first-use account must match the successful work's account; an initially anonymous first-use observation may convert after authentication. Shared install IDs with conflicting first-use accounts or classifications are excluded from cohort eligibility; conflicting first-use event keys remain visible to that ambiguity check even when a separate valid first-use event exists. Their telemetry and run diagnostics remain retained. Anonymous nonconverters stay in the denominator. Scheduled, eval, and unknown-origin work do not qualify for this activation numerator.
- **Retention:** W1 is activity in days 7 through 13 after first observed qualifying work, W4 in days 28 through 34, and W8 in days 56 through 62. Weekly cohorts are reported only when every member's follow-up interval has elapsed. A harness cohort starts at first confirmed use of that harness.
- **First requests:** First-attempt anchors span all hosting/segment slices of a harness; eligible identities and subsequent conversions are restricted to the selected slice. Conversions must occur within seven days of the identity's first attempt. Earlier legacy work remains evidence of an earlier attempt even when its timestamp is unavailable, so it cannot create a false newcomer. Detailed cohort/opportunity days are required. Unknown billing prevents a claim of no paid conversion; an observed known-paid conversion remains known despite another unknown charge.
- **Model adoption:** After seven complete detailed days, rank the top ten models by confirmed successful requests from identified accounts whose parent work is valid. Show adopting accounts, successful requests, known spend, and per-model known-cost coverage. Top-ten share plus Other share equals model-attributed share, all divided by the same confirmed-account request denominator; the remaining gap is unattributed model traffic. Missing windows and unavailable amounts stay absent.
- **Cohort progression:** SQL aggregates timestamped facts strictly within `[first_success_at, first_success_at + N days)` for N=1, 7, 30. No overlapping daily bucket is substituted for an exact interval. Anchors span all hosting/segment slices, separately for each account/install and aggregate/specific harness; cohort membership and throughput honor the selected slice. Monday-aligned cohorts report only after their follow-up windows and required detailed history are complete. D1/D7/D30 can refer to different cohorts, so tables expose their dates and eligible populations.
- **New-to-Ori vs new-to-harness:** Active identities are classified using first confirmed work across Ori, respectively on the selected harness. Complete first-work history is required. An existing Ori identity adopting another harness is new only to that harness. With `harness:all`, the two metrics coincide; select a specific harness to distinguish its new adopters from new Ori accounts.
- **History:** Collection starts prospectively with the first persisted product event. Reports expose complete history days and readiness. A missing materialization or immature window is unavailable. First-work cohorts become unavailable if the original collection history is truncated; persistent lifetime cohort anchors are a follow-up before the 400-day horizon.

## Scheduled reporting

The internal worker runs the product job daily at 04:47 UTC. It refreshes the latest eight closed UTC dates to cover seven-day arrival delays and upgrades at most seven additional missing/outdated detailed dates, newest first. A selected snapshot with a newer authorized cutoff is reused rather than rematerialized at an obsolete cutoff. `completedDays` tracks published history; `detailedDays` separately requires `fact_version >= 2`. Historical report reads reuse the prepared snapshots.

Postgres lease rows retain `(activity_date, report_end)` identities, while every claim, renewal, publication, commit and release serializes through a short transaction-scoped advisory lock for the activity date. Only one live day owner is admitted, and a cutoff older than the latest committed cutoff is rejected. Equal-cutoff replacement remains possible after expiry. Tokens are allocated after locks, and ownership is checked against database wall time after lock waits. Transactions never span ClickHouse calls. Preparation ownership lasts five minutes. Entering publication extends it to ten minutes so four 90-second ClickHouse operations and three 10-second writes leave commit headroom. Abandoned owners still expire and cannot authorize their staged data.

Timestamped generation facts, work/model aggregates, and the `is_leased:1`, `fact_version:2` marker become durable before the Postgres publication commit. The compare-and-set authorizes the exact snapshot only if token, identity, phase and ownership remain valid. Readers keep the previous committed snapshot during a failed replacement and reject orphan/expired-owner publications. Legacy markers remain readable but do not certify detailed capabilities.

Each read has a 90-second timeout and a 250,000-row result ceiling. Exceeding either fails the report instead of returning a truncated population. The job scans the generation ledger for each refreshed day and up to 400 days of product associations; production query cost still needs measurement during rollout.

Postgres `ori_product_report_deliveries` owns the delivery ledger, keyed by `(environment, metric_version, report_end)`. The version-2 worker schedules recoverable boundaries and processes the seven oldest pending reports plus the current boundary. A first-payload-wins update freezes the aggregate rows and exact outbound series once; retries reuse that payload. The freeze write itself retries up to three times with backoff: building a report is seconds of CPU with no I/O, and deployed Workers only advance the clock on I/O, so the Postgres client's 3-second connect timer armed right after the build is already due and fails the first connect at exactly 3000 ms. The failed attempt's socket I/O brings the clock current and the retry connects. Only that connect failure is retried; any other error fails fast, and a failure on the last attempt leaves the report pending and the run incomplete. Version-1 records remain separate historical records, not version-2 jobs.

All product gauges use the exclusive midnight report boundary as their fixed timestamp. Before sending, the worker checks that Datadog [historical metrics ingestion](https://docs.datadoghq.com/metrics/custom_metrics/historical_metrics/) is enabled for every emitted metric. Replaying the same gauge timestamp and tag set replaces the same logical point. Every chunk must be accepted before `accepted_at` is written; timeouts, partial delivery, process interruption and acknowledgment failures leave the job pending. `accepted_at` means intake acceptance, not query visibility: Datadog can take up to 14 hours to expose a 12-hour-to-30-day-old point, and longer for older points.

Every present measurement also emits `measurement_report_end_timestamp` with the same dimensions plus `measurement:<name>`; its value is the report boundary. Snapshot cards/tables use a 36-hour lookback to cover normal overnight scheduling and require each operand's witness to match the latest global report boundary. A newer report therefore suppresses an omitted old amount or disappeared model/cohort instead of borrowing yesterday's value. Unknown measurements emit neither a value nor a fresh witness; measured zero emits both. Historical timeseries retain fixed UTC points. Cohort series carry `cohort_start` and `cohort_end` tags.

Full report/cohort rows live in the ledger payload. The earlier aggregate report-log path is removed: Datadog logs accept only an 18-hour history and provide no documented idempotency key. Operational `ori_product_sync` logs identify pending boundaries and error locations without duplicating report rows. Activity, activation, retention, harness, and coverage metrics drive the dashboards. The public API service dashboard charts `openrouter.ori.product_persistence` outcomes (`stored`, `error`, `projection_rejected`, `scheduling_error`). Scheduling failures count eligible product events and issue a warning while preserving the HTTP 202 response.

Automatic catch-up covers 399 report boundaries: each boundary requires its previous UTC date, whose facts expire at date plus 400 days. Older queued rows remain in the ledger for inspection; reconstructing a never-collected report after its source history expires requires an external archive. A frozen report is an as-observed snapshot, so late evidence affects later reports rather than rewriting an already-published report. Metric-definition changes require a new metric version, not edits to frozen payloads.

## Account erasure

The `delete_clickhouse_ori_product_data` deletion target covers all current and superseded snapshots of events, work days, model days and timestamped generation facts. It installs a SHA-256 account-digest barrier for 401 days and drains pre-barrier writes for the shared SQL execution bound plus 30 seconds of cancellation headroom. It then waits for physical deletion mutations: locally on plain `MergeTree`, or on every replica for replicated engines. Reads and server-side inserts suppress the digest, and materialization rejects dates outside its wall-clock retention horizon. Failures remain retryable, never completed. Shared client-controlled install/session identifiers do not authorize deletion of another account or genuinely anonymous events. Financial ledger amounts are not changed by this target.

The barrier and identity tables must share the same storage topology: co-locate them in a non-replicated deployment, or replicate the barrier along with the identity tables. Digest-first ordering serves the deletion and writer-filter lookups; the TTL expires individual rows even when a part also contains newer barriers.

## Rollout and review

1. Apply the base ClickHouse migrations 256–258, then `263_add_generation_spend_knownness.sql`, `264_extend_ori_product_analytics_firsts.sql`, `265_add_ori_product_generation_facts.sql` and `266_add_ori_product_deleted_accounts.sql` before deploying readers or writers. The provenance migration adds a nullable metadata column to the inference ledger without changing amounts; the others create/extend independent analytics storage. Recheck numbering against the merge base before landing.
1. Apply the existing Postgres delivery/lease migrations and `20260918014438_add_ori_product_deletion_target.sql`, then regenerate database types. The new enum migration takes an `ExclusiveLock` on the enum object, not application tables; it performs no customer-table scan or rewrite.
1. Give the worker its own Datadog application key with both historical-metrics permissions. The key is the `DD_ORI_DASHBOARDS_KEY` secret of `cfw-internal`, read only by this sync and held in Infisical at `/services/cfw-internal-api` for each environment; in Datadog (us5) it is named `cfw-internal ori-product-sync`. It needs `metrics_read` to read a metric's historical configuration and `late_metrics_config_write` to create one: the worker enables historical ingestion itself for every emitted `openrouter.ori.product.*` gauge, including `measurement_report_end_timestamp`, the newcomer, milestone, model-coverage and progression metrics, so a key with only `metrics_read` fails on the first metric that is not yet enabled. Datadog offers no `late_metrics_config_write` key scope, so the key is an unscoped application key owned by a user whose role holds both `metrics_read` and `late_metrics_config_write`; it carries exactly its owner's permissions. `DD_API_KEY` in the same folder is the intake key. Every key rotation must carry both permissions forward, or every report stays pending on `ori-product-report.historical-config` with an `@extra.error_message` of `Datadog historical metrics configuration read returned HTTP 403; the application key is invalid or lacks the metrics_read permission` (or `... create ... late_metrics_config_write`), the CF Workflows run for `ori-product-analytics-sync` ends errored, and `[Ori] Product analytics sync has accepted no reports` alerts. Missing credentials, disabled history or failed configuration reads leave delivery pending. Metric retention must cover at least 400 days; Datadog's default 15-month custom-metric retention does.
1. After the grant, the first run bootstraps each never-seen gauge with a current point tagged `historical_bootstrap:true` and leaves its reports pending; the second run creates the configurations and delivers. Expect the backlog to start falling on the second 04:47 UTC run after the grant, or trigger `ori-product-analytics-sync` twice by hand through `POST /api/v1/internal/cron/trigger`.
1. Deploy provenance-producing code and the reporting/deletion workers through the normal release process. Confirm events, all three fact grains, authorized detailed markers, frozen version-2 payloads and intake acknowledgment before interpreting values. Old rows without provenance remain unknown, and detailed cohorts remain unavailable until their required history is rebuilt.
1. Release the Ori instrumentation through the normal release process. New clients report event IDs, observation stage, and attribution capability; native Ori sends its resolved session header on inference requests. No release is performed by this change.
1. Preview the dashboard modules in a temporary Terraform state, read them back through the Datadog API, and replay persisted queries before production apply. Early cohort panels are expected to have no data until their windows mature.
1. CI planning and release apply forward GitHub's existing `DD_WEBHOOK_SECRET` as `TF_VAR_dd_webhook_secret`. This does not verify parity with the deployed worker, and the current webhook configuration does not enforce a nonempty value. Credential configuration remains an operational responsibility, outside Ori metric validation.

To pause reporting, remove the daily task through the normal deployment process. Existing inference and CLI execution do not depend on these analytics tables. Retain stored facts while investigating rather than deleting collection history.

On tilt, `internal` sends these calls to `datadog-fake` (`dev/datadog-historical-metrics-fake.ts`) through `DD_API_BASE_URL`, never to the real Datadog org. Its `refuse-read`, `refuse-create` and `accept` buttons reproduce the production 403s and the accepting path; fire `47 4 * * *` from the `internal:cron` button and read `ori_product_sync` in `tilt logs internal` and the calls at `http://localhost:8843/__fake/requests`.

Local verification uses real ClickHouse 25.8.23 and Postgres, exact-window/compaction/deletion integration scenarios, and the dashboard semantic regressions. Replay metric queries through Datadog's scalar/timeseries APIs with both aggregate and selected-harness scopes. A metrics-read key does not grant dashboard read/write or UI access; successful query execution is not evidence of a persisted or visually reviewed dashboard. Use an authorized private preview for that final readback, never a public sharing token.

Inspect pending reports and frozen rows in Postgres through the repository's database tooling:

```sql
SELECT environment, metric_version, report_end, payload IS NOT NULL AS is_frozen, created_at
FROM ori_product_report_deliveries
WHERE accepted_at IS NULL
ORDER BY environment, metric_version, report_end;

SELECT payload -> 'rows' AS report_rows
FROM ori_product_report_deliveries
WHERE environment = 'production' AND metric_version = 2 AND report_end = DATE '2026-09-10';

SELECT activity_date, report_end, source_version, expires_at, is_publishing, published_snapshot_id
FROM ori_product_materialization_leases
WHERE expires_at > clock_timestamp()
ORDER BY activity_date, report_end;
```

## Further instrumentation

The report does not measure user satisfaction, setup abandonment, auth funnel steps, human submissions, tool-call depth, preferred-harness switching, or local `/usage` history accuracy. Those require additional bounded lifecycle signals and the Ori RFC process. Successful inference and technical completion must not be renamed task success.

The OTEL section contains aggregate daemon metrics only, not span queries or correlated customer/run/request journeys. Runtime spans carry `ori.openrouter.session.id`, but per-request generation IDs are not exported in OTLP and failed attempts lack them. A producer-side lifecycle contract for bounded completed/failed generation IDs is required before adding per-request linkage. Until then these panels are execution diagnostics, not adoption or task-success totals.
