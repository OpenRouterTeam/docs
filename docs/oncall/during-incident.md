# During an Incident

> [!NOTE]
> Start with [First 15 minutes](./first-15-minutes.md). Continue here to restore service and keep the customer informed.
>
> Not an incident? Record the finding and evidence in the alert thread or ticket and any existing incident. Engineering resolves any precautionary incident; then close the page, keep the ticket open for follow-up, and fix the monitor if needed.


| Stage              | Engineering                                                                                                                                                                                                                                                                                                                                                 | Support                                                                                                                                                                                                                                             |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Join**           | - Join the Datadog incident; link the alert thread and any Pylon ticket.<br>- The on-call engineer is the incident commander by default and stays commander until another engineer explicitly accepts the role in the incident channel.                                                                                                                                                                                                                        | - Join the incident and link any Pylon tickets.<br>- Monitor Pylon for related tickets; link them and apply the customer updates below to each.<br>- Tell customers with linked tickets an incident is open.                                                                                                                                                          |
| **Triage**         | - Check errors and latency for affected models, providers, and regions.<br>- Review the last six hours of deploys, flags, routing, and provider config changes.<br>- Try to reproduce the issue.<br>- Follow the monitor’s runbook. No runbook? Work through the checks above.                                                                                                                         | - Gather request IDs, affected models, start time, and whether the issue persists.<br>- Check other tickets and provider status pages.<br>- Update incident impact and timeline.                                                                    |
| **Mitigate**       | - Choose the safest available action to reduce customer impact. Keep any active release freeze in place; use the [Hotfix workflow](https://github.com/OpenRouterTeam/openrouter-web/actions/workflows/hotfix.yaml) for a deployment needed to mitigate the incident.<br>- Post findings and changes in the incident channel before or as you act.<br>- Recheck whether impact has spread beyond one customer.                                                                                                                 | - Update the customer every **30 min for SEV-1** or **60 min for SEV-2**, even if nothing has changed. Use the [customer update templates](./template-customer-update.md).<br>- Share only what Engineering has confirmed in the incident channel. |
| **Public status**  | - **2+ customers affected?** [Publish a notice](https://us5.datadoghq.com/status-pages/3bdfe680-d6e4-4a0b-9c04-c25058c342e0/notices) if none is open: **Major outage** for SEV-1, **Degraded performance** for SEV-2.<br>- Update it as impact changes and when recovery is being monitored. Use the [public status templates](./template-status-page.md).<br>- Post the notice’s public link from [status.openrouter.ai](https://status.openrouter.ai/) in the incident channel. | - Reuse that public link in customer updates.<br>- Flag new customer impact to Engineering.                                                                                                                                                                |
| **Escalate**       | - Bring in an expert if the affected area is clear.<br>- **No traction by T30?** Bring in an expert or [page Secondary](https://us5.datadoghq.com/on-call/schedules).<br>- Stay involved and work with the expert until mitigated.                                                                                                                                                                         | - Track time since the page and remind Engineering at **T30** if there is no progress.<br>- Help contact the expert or Secondary.                                                                                                                   |
| **Mitigated**      | - Confirm metrics are back to baseline across affected models, providers, and regions. Where practical, retry previously failing requests and confirm they succeed.<br>- Record the recovery evidence.<br>- Declare mitigated and watch for recurrence. Keep any release freeze in place while verifying recovery.                                          | - Tell the customer and ask them to confirm recovery.<br>- Report any continuing impact to Engineering.                                                                                                                                             |
| **Resolved**       | - Resolve when customer impact has ended and recovery is verified; no need to wait for a customer reply.<br>- Mark any public status-page notice resolved.<br>- Assign remaining investigation and corrective work in Linear. Root cause need not be known yet.                                                                                             | - Send the final update and close the ticket using [After an incident](./after-incident.md).<br>- Customer silence alone is not recovery evidence.                                                                                                  |
| **Release freeze** | - After verified recovery, the incident commander lifts any active freeze when releases are safe to resume: run [Release Freeze](https://github.com/OpenRouterTeam/openrouter-web/actions/workflows/release-freeze.yaml) with `is_frozen` unchecked and a note, then say so in the incident channel.<br>- If it must stay, record the owner, reason, and next review time in the incident.                                                                                                                                                           | - Track the next review time if the freeze stays in place.                                                                                                                                                                                          |
