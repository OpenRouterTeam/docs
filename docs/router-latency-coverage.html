Where a request spends its time, and what router latency sees of it

A chat request to cfw-api passes through about 28 steps between the worker receiving it and the last background write. Router latency measures two windows of that path and subtracts the time we spend waiting on providers, tools and guardrails. This page puts every step on that timeline and marks whether it counts as OpenRouter time, gets subtracted, lands in the wrong bucket, or falls outside both windows.

Bottom line

For plain chat traffic, router_latency_v2 + post_dispatch is the best number we have. Across all traffic, 5 request paths emit no number at all. Our stream CPU overlaps the provider, so the delay it adds is reported separately as stream delay.

router_latency_v2 = (firstUpstreamDispatchAtMs - startedAtMs) - excluded
post_dispatch     = (lastByteToClientAtMs - firstUpstreamDispatchAtMs) - excluded
unexplained       = router_latency_v2 window - every recorded interval   // reported, never subtracted

excluded causes   upstream  retried_providers  parsing  tools  guardrails  routing_models  agent_loop
own phases        bootstrap  auth  body_read  preset_resolution  credit_authorization
                  model_selection  sticky_session  private_catalog  rate_limit
                  spend_guard  request_build  prompt_cache  media_hydration
                  response_cache  known_csam
