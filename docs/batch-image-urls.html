Batch now admits public image URLs — but never base64.

The Batch API used to reject every non-text content part outright. This change carves out one case: an image_url part is allowed when its URL is a public http(s) link and the resolved model + batch provider can carry a URL natively (OpenAI, Anthropic). Everything else — data:/base64 images, audio, video, files, and Vertex Gemini image lines — is still rejected with a 422. Output stays text-only.

Why now Batch was text-only for a T&S reason (OPE-4826): don't store media we can't vet. A public URL is a reference, not stored bytes — so URL-only image input is the safe, minimal carve-out.

The two gates are different questions

Guard 1 (assert-supported-batch-content.ts) asks "is this content shape allowed at all?" — it lets an http(s) image URL through but blocks base64. Guard 2 (image-input-capability.ts) asks "can this specific model + batch provider actually carry that URL?" A line must clear both.

03

The one line that flips a URL from "reject" to "allow"

assert-supported-batch-content.ts

Previously any part whose type was non-text (including image_url) was returned as offending. Now an image part is routed through a URL classifier first, and only base64/malformed URLs offend. 

// an image part is judged by its URL, not just its type
const hasImageURL = isDefinedAndNotNull(parsed.data.image_url);
if (type === 'image_url' || hasImageURL) {
  return isAllowedImageURL(parsed.data.image_url) ? null : 'image_url';
}

function isAllowedImageURL(value: unknown): boolean {
  if (!isImageURL(value)) return false;
  const parsedURL = mapToParsedDataURL(value.url);   // same classifier the sync path uses
  return isOk(parsedURL) && parsedURL.data.type === ParsedDataURLType.URL;
}

No new fetch surface

Batch lowering runs the sync serializers without hydrating the URL to base64, so the original URL reaches the provider and the provider fetches it — not OpenRouter. No new SSRF surface beyond what sync already has.
