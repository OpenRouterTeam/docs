# HIPAA PHI leak response (ENT-2008 leak detector)

What to do when the continuous HIPAA leak detector fires, how to triage a finding from a generation id, how to contain each sink, and what the detector does not cover. The detector is the Stage One "continuous leak monitor" control of the HIPAA RFC: it verifies, every fifteen minutes, that no HIPAA-flagged generation has reached a non-HIPAA sink, and routes a hit into the Stage Zero incident-response procedure for PHI leakage rather than onto a dashboard. Built under [ENT-2008](https://linear.app/openrouter/issue/ENT-2008) as a three-PR stack: the rules library (`packages/clickhouse/hipaa-leak/`), the `cfw-internal` cron (`services/cfw-internal/src/routes/cron/hipaa-leak-sweep.ts`), and the monitors plus this runbook (`configs/terraform-monitors/monitoring/hipaa_leak_detector.tf`).

- **Owner:** Ben Heidorn (HIPAA project lead, ENT-2008 assignee).
- **Alert destination:** `@slack-OpenRouter-alerts-hipaa` (`#alerts-hipaa`), the channel every other `[HIPAA]` monitor pages. There is no BAA-covered destination to route to, so the control is on the payload (see `configs/terraform-monitors/HIPAA.md`): the Slack message carries the rule id, the sink name and a count, nothing else.
- **Monitors:** `[HIPAA] Leak detector: HIPAA generation found in a non-HIPAA sink`, `[HIPAA] Leak detector sweep failed`, `[HIPAA] Leak detector heartbeat missing`.
- **Dashboard:** the `internal` instance of the cfw service dashboard (`configs/terraform-monitors/monitoring/cfw_service_dashboard.tf`), App metrics tab, `openrouter.hipaa_leak_sweep.*` widgets.
- **Log events (Datadog, `env:production service:api @script_name:internal`):** `hipaa_leak_detected`, `hipaa_leak_sweep_failed`, `hipaa_leak_sweep_ok`.

## What the detector checks

Every run loads the HIPAA workspaces from Postgres (`listHipaaWorkspaces`, soft-deleted included — a leak from a deleted HIPAA workspace is still a leak), builds a sliding two-hour window ending now, and evaluates three rules. Every query is scoped to the HIPAA entities and the window, so the sweep reads only HIPAA rows and objects and is a primary-key range read on each table.

| Rule id | Sink names | What a finding means |
| --- | --- | --- |
| `scrub_column_populated` | `clickhouse_generations`, `clickhouse_endpoint_requests`, `clickhouse_guardrail_events`, `clickhouse_user_signals` | A row the HIPAA worker wrote (`is_hipaa_generated = 1`, or for `guardrail_events` / `user_signals` a row whose `generation_id` is a stamped generation) still carries a value in a column its HIPAA field policy scrubs. The column list is derived from the policies in `packages/clickhouse/*/hipaa.ts` at query time, and the log line names the populated columns in `@extra.column_names`. Means the submission boundary (`applyHipaaPolicy`) was bypassed or a writer skipped it. |
| `dispatch_miss` | `clickhouse_generations`, `clickhouse_endpoint_requests` | A HIPAA workspace's row was written without the stamp, later than the workspace's dispatch-miss lower bound (`updated_at` plus a 15-minute propagation grace, or the window start). Means the primary `api` worker served a HIPAA request instead of dispatching it to the mirror, so the full unscrubbed row reached the shared table — and every other primary-only sink (prompt storage, classifiers, broadcast) may have been written too. |
| `prompt_log_object_present` | `r2_chatml_prompt_logs`, `r2_raw_prompt_logs`, `r2_formatted_prompt_logs`, `gcs_customer_prompt_logs` | An object exists at the generation's prompt-log key (`<entityId>/<generationId>.json` in R2; `<entityId>/<generationId>/<generationId>-full.json` in the customer GCS store) for a HIPAA generation of the window. The mirror never writes any of these (`getNonPrivateLoggingDecision` and `getIsPrivateLoggingEnabledForRequest` both refuse on HIPAA), so presence is a leak of the prompt itself. The check is a metadata `head`, never a body read. Every read is a Worker subrequest, so a run spends at most `MAX_OBJECT_CHECKS_PER_RUN` (8,000, the 10,000-per-invocation ceiling minus a setup reserve) on object checks — 2,000 generations across the four stores, newest first, over the whole two-hour window. A window that held more than that logs `is_object_check_truncated: true` and a `hipaa_leak_sweep_failed` line for this rule with `sink_name: none` whose `error_metadata` carries `checked_count` and `cap`; the oldest generations of that window were not checked. |

## Triage from a generation id

1. Open the `hipaa_leak_detected` line in Datadog (link in the alert). Read `@extra.rule_id`, `@extra.sink_name`, `@extra.generation_count` (exact), `@extra.generation_ids` (first 20, comma-joined), `@extra.column_names`, `@extra.workspace_ids` and the window bounds. Do not paste ids or column names into Slack; the incident channel is not inside the BAA boundary either.
2. Decide which store holds the data from the sink name: `clickhouse_*` is the shared ClickHouse table of that name; `r2_*` is the R2 bucket of that name bound to cfw-internal (`services/cfw-internal/wrangler.toml`); `gcs_customer_prompt_logs` is the `global-private-prompt-data` GCS bucket.
3. Decide the failure class from the rule id. `scrub_column_populated` is a boundary bug on the HIPAA worker: find the writer for that table that does not go through `toHipaa*` (or a column the policy classifies wrongly) and fix it. `dispatch_miss` is a routing failure: check the HIPAA dispatch metrics (`openrouter.hipaa_dispatch.*`, monitors in `hipaa_dispatch_refusals.tf`), whether the workspace was enabled inside the last few hours (an ENT-1859 activation-pending propagation, the emergency auth-cache tier can serve the old posture for up to 12 h during an auth-service outage), and whether the mirror was healthy. `prompt_log_object_present` with no `dispatch_miss` finding for the same generation means a HIPAA-worker write path leaked; with one, it is the consequence of the miss.
4. For `dispatch_miss`, list the full population before containing: the rule reports 20 ids but `generation_count` is exact, and the ClickHouse query in `packages/clickhouse/hipaa-leak/dispatch-miss-rule.ts` can be run by hand for any window (the `listHipaaGenerations` query gives the ids with their entity ids for the object checks).
5. Confirm scope: how many generations, which workspaces, over what span; whether the leak is ongoing (the finding recurs on each run while the data is in the window) or historical. Only then contain.

## Containment per sink

Containment is deletion or scrubbing of the leaked copy. It does not undo the exposure; record what was where and for how long in the incident.

- **ClickHouse rows (`clickhouse_*`).** There is no per-generation scrub tool in this repo yet. Containment is an `ALTER TABLE <table> UPDATE <column> = <empty> ... WHERE generation_id IN (...)` mutation for a `scrub_column_populated` finding (empty values per column are the `SCRUBBED_*_VALUES` tables in `packages/clickhouse/*/hipaa.ts`), or a lightweight `DELETE FROM <table> WHERE generation_id IN (...)` for a `dispatch_miss` row that should never have existed in the shared table. Both are run by an operator with write access to the production cluster and recorded in the incident; a reusable, operator-reviewed backfill on the backfill platform (`.agents/skills/add-reviewed-backfill/SKILL.md`) is the right shape if this recurs. The `endpoint_requests_by_generation_v1` materialized view and the `endpoint_requests_clickpipe` table receive the same rows; scrub those too.
- **R2 prompt logs (`r2_*`).** Per generation, use the Mission Control "Delete Logged Prompt" tool (`projects/mission-control/app/admin-utils/delete-logs/`), which probes and deletes the ChatML and Raw objects and the customer GCS object, or the audited route `DELETE /api/v1/internal/prompt-logs/:bucket/object?key=...` on cfw-internal (`services/cfw-internal/src/routes/prompt-logs/route.ts`). The Mission Control tool does not touch the Formatted bucket: an `r2_formatted_prompt_logs` finding is contained through the audited route with the `formatted` bucket slug. Both go through the same audited path, and that path first copies the object to `_trash/<entityId>/<ISO time>/<generationId>.json` in the same bucket; the route refuses any `_trash/` key, so **no per-generation tool can purge the recovery copy early**. The PHI therefore remains in the bucket, under the trash prefix, until the `prompt-logs-trash-sweep` cron removes copies older than `TRASH_RETENTION_DAYS` (14 days); the incident record must state that. The only in-repo path that removes trash copies sooner is the whole-entity data-deletion workflow (`services/cfw-internal/src/workflows/data-deletion.ts`, target `delete_r2_prompt_logs`), which deletes every object under `<entityId>/` and `_trash/<entityId>/` through the bucket bindings — every prompt log of that entity, not only the leaked generation. There is no documented raw-credential path; do not invent one.
- **Customer GCS prompt logs (`gcs_customer_prompt_logs`).** Same Mission Control tool, or the workflow's `delete_gcs_prompt_logs` target for a whole entity.
- **Downstream of a dispatch miss.** A request the primary served may also have reached the classifier and broadcast queues and the customer's own broadcast destinations; those are point-in-time and not recoverable from here. Note them in the incident.
- **Datadog.** If a leaked value reached a log line (the detector itself never logs one), the purge path is [ENT-2027](https://linear.app/openrouter/issue/ENT-2027), which is still Todo; until it lands there is no log-content purge and the incident record must say so.

## Sweep failed

A `hipaa_leak_sweep_failed` line means one rule against one sink was not evaluated; the alert fires on two failures of the same rule and sink within an hour. `rule_id: none` means the run failed before any rule ran: the HIPAA workspace list could not be read from Postgres, the list hit its 10,000-row cap (coverage is then incomplete), or ClickHouse env was missing on the worker. `rule_id: prompt_log_object_present` with `sink_name: none` means the object rule had no complete population: the HIPAA generation listing failed, or the window held more generations than the object-check budget covers (read `checked_count` and `cap` off `error_metadata`; the cap is `MAX_OBJECT_CHECKS_PER_RUN` divided by the store count, 2,000 today). A store that errors stops being probed once 8 errors have landed — at most 15 calls, budget plus concurrency minus one — and reports `error_count`, `checked_count` and `unchecked_count`. If truncation recurs run after run, HIPAA volume has outgrown one invocation and the object rule needs fanning out across invocations (a queue or workflow per store); that is a code change, not an operator action. Read `error_name`, `error_message` and `error_location` on the line. `error_name` is bounded: `setup_failed` (the run never started), `rule_query_failed` (a ClickHouse rule or the generation listing errored), `object_population_truncated` (the budget case above), `object_check_error` (a store returned or threw an error) and `object_check_timeout` (a store's metadata requests exceeded the 10-second per-check deadline; `error_metadata` carries `timeout_count`). A timeout points at that store's health — R2 or GCS status, cfw-internal's egress — not at the detector; the sweep stopped probing that store after its error budget and reports the remainder as `unchecked_count`, so the store is unverified for that run, not clean. While a rule is failing its sink is unverified, not clean. The two-hour lookback re-covers a gap shorter than that; for a longer one, run the affected rule's query by hand for the missed window (`packages/clickhouse/hipaa-leak/`, the SQL builders are exported and unit-tested).

## Heartbeat missing

No ok / detected / failed line in an hour means the cron did not run. Check the `*/15 * * * *` trigger in `services/cfw-internal/wrangler.toml`, the matching slot in `services/cfw-internal/src/routes/cron/schedule.ts` (`services/cfw-internal/src/cron-triggers.test.ts` pins them 1:1), the `cron-task-workflow` instances in the Cloudflare dashboard, and cfw-internal worker health. The gap is unverified until the sweep resumes, and the next run's two-hour lookback covers it only if the outage was shorter than two hours; for a longer one, run the rules by hand for the gap (the SQL builders in `packages/clickhouse/hipaa-leak/` are exported and unit-tested).

## What the detector does not cover

- **Spanner (usage-record).** The CF fleet must not talk to Spanner directly; it is reached only through the `SVC_USAGE_RECORD` binding, which exposes no read suited to this. The mirror is expected to write stamped, prompt-free generations there, and `tests/e2e/api/hipaa/sink-isolation.test.ts` asserts that point-in-time. A Spanner rule is a follow-up once usage-record exposes a scrub-column read.
- **Datadog log content.** Whether a HIPAA log line carries PHI is [ENT-2026](https://linear.app/openrouter/issue/ENT-2026)'s Sensitive Data Scanner, not this detector; this detector's own lines carry identifiers and counts only, and `bun run check:hipaa-monitor-payloads` holds its monitors to that.
- **Queues and their consumers (classifier, broadcast, prompt-upload queues, customer broadcast destinations).** Point-in-time only: `tests/e2e/api/hipaa/sink-isolation.test.ts` and the canary in `packages/router/tests/hipaa-canary/` prove nothing lands for a mirror-served request, with a positive control on the primary. Nothing re-verifies that continuously; a `dispatch_miss` finding is the signal that these were probably written too.
- **Rows that reach ClickHouse more than two hours after their `created_at`** (a manual dead-letter replay). They are outside every later window; run the rules by hand after such a replay.
- **A Files object uploaded during the enable window.** The enable's files-api presence check (`assertWorkspaceEnablePreconditions` in `services/cfw-frontend-api/src/routes/workspace/workspace-settings/enable-workspace-hipaa-handler.ts`) and the flag commit are two statements, and an R2 upload is serialized against neither, so an object that lands under the workspace prefix in between is caught by no check and by no rule here. Once the flag is set it is unreachable through the Files API: `guardFilesWorkspaceHipaa` (`services/cfw-files-api/src/files/resolve-context.ts`) refuses every route for the workspace, including `DELETE /api/v1/files/{file_id}` and the dashboard's `bulk-delete-all`, which is that route in a loop. No in-repo path removes it afterwards — workspace deletion is a soft delete with no storage step (`packages/db/workspaces/delete-workspace-if-not-last.ts`), and the data-deletion workflow (`services/cfw-internal/src/workflows/data-deletion.ts`) has no Files target ([ENT-2167](https://linear.app/openrouter/issue/ENT-2167)) — so removal is out-of-band bucket access against `R2_FILES` / `R2_FILES_EU`, recorded in the incident.
- **A HIPAA workspace updated often.** The dispatch-miss bound is `updated_at`, an upper bound on when the flag flipped, so frequent unrelated updates hide unstamped rows before the latest one. A recorded HIPAA-enable instant is the right future source for the bound. Postgres does not keep one today; [ENT-1995](https://linear.app/openrouter/issue/ENT-1995) ([#40985](https://github.com/OpenRouterTeam/openrouter-web/pull/40985), open) adds `workspace_hipaa_flag_audit` with an `enabled` row per flip, which would supply it once it lands — but only for workspaces enabled after that table exists; a workspace enabled before it gets no `enabled` row, so the `updated_at` bound remains needed for those. The rule never false-positives on pre-enable rows.

## Escalation

1. Acknowledge in `#alerts-hipaa` and open an incident under the Stage Zero PHI-leakage procedure; the owner above is the incident lead until handed off.
2. Contain per sink as above; record store, generation count, span and containment time in the incident.
3. Root-cause by rule id (boundary bug, routing failure, or a writer that bypassed the mirror's gates) and ship the fix with a regression test — the e2e sink-isolation suite or a ClickHouse integration test in `packages/clickhouse/integration/hipaa-leak/` is the place.
4. Notify per the BAA and the customer contract for the affected workspaces; that decision belongs to the incident lead and legal, not to this runbook.
