# Model Launch Runbook

How to launch a model on OpenRouter using all our systems: Mission Control, Devin, and Buddy. The agents carry the detailed how-to in their skills — your job is orchestration, judgment calls, and the edge cases below.

Every production write follows the same lifecycle: **preview → your explicit approval → apply → re-read the persisted record and compare it to the approved preview**. A successful response or created ID is not verification; before approving, `stripped_fields` must be empty or explicitly understood. Every mutation gets its own gate — model/endpoint create or patch, pricing, data policy, aliases, privacy, visibility, capability-test applies, hide/unhide. "Stage it" or a Devin→Buddy handoff never authorizes a write.

## TL;DR

In general you should be able to accomplish an entire model launch in a single Slack thread with Devin and Buddy.

| Step | Owner |
|---|---|
| Gather launch inputs (§0) | Human |
| Vendor capability probe, pricing, code PRs (§0–§1) | Devin |
| Review, merge, and deploy Devin's PRs | Human + Perry |
| Provider / model / endpoint staging and production writes (§2) | Buddy |
| Approval for Buddy's production DB writes | Human |
| Flag any promo / discount / free pricing to GTM (§2a) | Devin + Buddy |
| GTM comms to top apps and customers (§2a) | Human (GTM) |
| E2E generations (if media, used for featured playground examples) (§3, §3b) | Buddy |
| Verify generated E2E results (§3) | Devin |
| [images + video] Approve and assign primary model example (§3a) | Buddy |
| Public visibility flip (§4) | Buddy |
| Final visual checks on openrouter.ai | Human |
| Social launch thread (Typefully) (§5) | Buddy |
| Post-launch monitoring (§6) | Devin |

Run this runbook top to bottom as an explicit checklist. Do not skip, reorder, or mark a step not applicable unilaterally. Only a human may waive a step, and the waiver must record who granted it. Verify anything reported done against the live record before ticking it, whether the claim came from a human, an agent, or an earlier session. A claim, Slack message, or created ID is not verification.

## 0. Collect launch inputs

**Commercial/legal status is a launch input**: contract signed, per-provider licensing scope confirmed (only unhide providers the lab has licensed — passing tests isn't a license), and a real default data policy on new providers (a null one means retention terms were never decided).

From the provider/lab thread: exact slugs (public + dated permaslug, variants like `:free` / `:fast`), upstream model IDs **per provider** (1P, Vertex, Bedrock etc. often differ — e.g. `claude-sonnet-5` vs `anthropic.claude-sonnet-5`, plus `global.` / `us.` / `eu.` prefixes; watch word ordering — `claude-fable-5`, not `claude-5-fable`), pricing per SKU per endpoint, context length, all modalities (briefs are rarely exhaustive — ask explicitly about file/audio/video input), reasoning config, data policy per variant (free vs. paid usually differ), HuggingFace page or release blog, launch time + timezone ("PST" in July means PDT), embargo status, and whether the launch carries promotional pricing (free variant, $0 or discounted rates, a time-limited promo period) plus its end date — see §2a. Reuse the existing catalog author slug (`meituan`, even if HF says `meituan-longcat`). Unknown beats fabricated: leave fields like `total_parameters` null until the provider gives a real number ("xxT" is not a number). Don't stage guessed public-facing fields — ask.

Permaslugs: clean public slug + `YYYYMMDD` suffix. Buddy defaults the suffix to today (UTC) unless you supply the intended date — confirm it in the preview (launch dates slip). Never rewrite legacy permaslugs to fit the convention.

For a ZDR or in-region-routing launch, also confirm up front which variants are in scope, whether the provider-side ZDR (or region-restricted) org/account exists and its key has been generated, the name of that credential, the per-region upstream model IDs, the per-region rate card, and the data-policy ID per variant (§2b). Assign owners up front: a **primary and a secondary DRI** on code + endpoint ops, another on social/docs. Don't make the endpoint operator also own launch comms.

## 1. Pick the path

The real split is not open-weight vs. proprietary — it's **existing provider + existing interface behavior (usually DB-only)** vs. **anything new** (new behavior, routing, provider, modality, or a registered frontier family), where Devin determines the required code first.

**DB-only launch** (most launches on existing providers): go to step 2 — Buddy stages the model + endpoints, ideally by cloning a sibling's config.

**Frontier family** (a Claude Fable 5, new GPT, etc.): needs a code PR in `openrouter-web` before launch. Ask Devin — the `onboard-frontier-model` skill covers it. Watch for:
- **Embargo**: no marketing name or permaslug in PR titles (the permaslug leaks the name). Merging the registration PR is safe — visibility is DB-driven — but **docs/migration-guide PRs publish on merge**, so hold those until go-live. Ask Devin to run a leak check before merging anything.
- **Behavior changes vs. the predecessor** (dropped params that now 400, new reasoning modes/effort levels): most are handled by DB config levers, not code — have Devin analyze the lab's guide first and tell you what's config vs. code. If breaking, ask Devin for a **migration guide** docs PR.
- **Opt-in policy lists** (provisioned throughput, refusal-fallback, new-account rate limits) are deliberate product calls, not registration — decide explicitly.
- A follow-up PR often catches missed aliases/mapper families/tests.

**New provider**: provider identity PR first, then adapter + monitor (Devin). Once that code is merged **and deployed**, Buddy can create the provider row itself (`POST /providers`, preview → approve like everything else): it validates the provider/adapter/pricing strategy against code enums, requires the code-defined permaslug, rejects duplicates (including hidden/deleted rows), and creates the provider unhidden (harmless with zero endpoints). `base_url` / `adapter_name` / `pricing_strategy` are create-only for Buddy (humans can still edit them in mission control afterwards); Buddy has no provider delete route (deleting — and reviving — a provider stays a human mission-control operation). The provider API key must be provisioned as a prod secret — an easy miss.

**Seed / BytePlus model** (Seed LLMs, Seedream, Seedance): not a standard flow — BytePlus console activation, a hard-coded `ep-` endpoint mapping, and a vendor-controlled metadata API gate (video models never enter it). Devin's `seed-byteplus-model-launch` skill covers it end to end.

**New modality** (TTS, STT, image, video, rerank, embeddings): Devin follows the per-modality onboarding skill family (`audio-provider-onboarding`, `image-provider-onboarding`, `video-provider-onboarding`, `rerank-provider-onboarding`, `embeddings-provider-onboarding`) — ask for a plan before code. Each family runs research → adapter → local staging → local e2e; the research phase takes capabilities dropped in the launch thread as its primary input, and the adapter PR must extend the serving capability enums to the provider's full advertised parameter surface in the same PR. Watch for:
- **Pricing needs a real rate card** — never stage on an estimate. Verify against the provider's public international pricing page (not their China/regional rates), and confirm the billing unit (per character, per second, per image).
- A provider's new modality often lives on a **different API host** than its chat API — Devin/Buddy handle the override, but scope it explicitly.
- **Stick to platform norms** (e.g. all TTS paths stream) — a deviation should be a flagged decision, not a default.
- **Never assume OpenAI conventions transfer** — the most repeated failure shape is an OpenAI-flavored default leaking to a provider with different semantics (`alloy` sent to voiceless TTS providers, omitted aspect ratios rejected). Sweep every default-synthesizing surface (adapter, playground, test runners, baseline tests) and test the minimal no-optional-params request end to end.
- **TTS needs voice metadata staged** — otherwise voices don't render on the model page/playground and default-voice injection bugs go unnoticed.
- Adapter PR and DB staging are **decoupled** — Buddy can stage hidden rows before or after merge, but never unhide until the adapter PR is deployed to prod.
- **Image models — update the live matrix** (easy miss). After the model/endpoint is live in **prod discovery** (or right after unhide), update [`tests/manual/api/images/generations/MATRIX.md`](../../tests/manual/api/images/generations/MATRIX.md) — its "How this file stays current" section documents the regen command, the hand-authored sections, and the `adapter-coverage.test.ts` CI gate that fails until a new adapter or passthrough key has live-case coverage.

## 2. Stage model + endpoints (Buddy / Mission Control)

Ask Buddy in Slack. **Stage and verify everything hidden well ahead of launch** — don't save applies for launch day. Visibility/privacy changes are a separate launch-time operation with their own fresh preview and approval. Edge cases:
- **Capture rollback material before writes**: current model/endpoint state, pricing JSON + version IDs, alias membership, visibility/privacy state. Pricing versions have no delete route anywhere — not just for Buddy; the DB layer is append-only and mission control can't remove one either — so never send exploratory payloads there.
- **Clone-first, by default**: Buddy should always model new endpoints on an existing endpoint from the same provider (ideally the previous-gen model — e.g. an existing Gemini model when adding a new Vertex endpoint); provider-specific settings like `provider_region: global` on google-vertex are easy to miss otherwise and break the endpoint outright. But the sibling is a template, not truth: copy structure and change only what differs — model facts (context, output limits, quantization) must come from the new launch source, never the sibling (a cloned 262K context shipped for a 1M model). Have Buddy classify every inherited nontrivial field: confirmed necessary, confirmed harmless, pending validation, or removed. Known misses: `provider_region` left null (broke google-vertex endpoints that needed `global`), inconsistent excluded params across endpoints, wrong provider slug (`google-vertex`, not `google`), and `discount_to_user` copied from the reference endpoint's pricing — never carry a discount over unless explicitly instructed.
- **Enumerate all endpoints first**: a model can have AI Studio/Vertex/Batch or 1P/Azure/regional endpoints — the model page is not the endpoint list. Scope explicitly (e.g. "batch deferred") and price each endpoint independently even when rates match.
- **Context changes are paired updates**: the model's context length AND each endpoint's prompt cap — a model can advertise a big window while an endpoint field silently caps it.
- **Pricing is irreversible and immediate**: a pricing version replaces the whole pricing JSON (no partial patch). "Irreversible" means already-charged usage and the version history — the *rates* are a two-way door: apply a new version (Buddy or mission control) to revert them. Service tiers (flex/priority) are separate endpoint rows with their own pricing — verify each tier row's rates against the provider pricing tab; don't copy from older models, and don't create 1P-only tier rows for Azure endpoints. A blank cache-write field may be a UI-completeness issue, not a billing bug — but a missing SKU is: enumerate every cache SKU the provider bills, including TTL-differentiated cache writes (a missing 1h rate silently bills at the base input rate).
- **Providers don't reprice in lockstep**: verify each provider's own price page — never propagate a 1P price change to other providers on assumption. Discounts stack (promo × service tier) — make stacking an explicit decision.
- **Multi-provider launches**: stage the direct endpoint first; hold others until their upstream IDs and pricing are confirmed. Regional endpoints often carry a surcharge (e.g. +10%, cache SKUs included).
- **Promotional pricing**: the pricing version always stores the **list rate**; express the promo as endpoint-level `discount_to_user`, never baked into `pricing_json` (a baked-in discount is invisible, survives repricing, and has no reversion path). On a live model, apply the discount **before** correcting a baked-in price so no request window bills at full list. The pricing resolver honors future `effective_at` values, but no current write path (Buddy or Mission Control) exposes an effective date — so in practice, schedule a real reminder for the reversion date. A promo is also a GTM event (§2a).
- **Descriptions** are public copy — house style, real source material, no hype or stale benchmarks. Configs drafted without source access ship bad descriptions; always revise.
- **Data policy**: verify the *effective* policy per endpoint, not just the override ID (ZDR and in-region variants have their own rules — §2b) — free and paid variants may differ, and ZDR means prompts are actually not retained. Video-generation endpoints must be staged with a non-ZDR endpoint data policy and must never inherit a ZDR provider default: `seed` and `google-vertex` both default to `retainsPrompts: false`, which is correct for their text endpoints and wrong for video. The routing layer forces video endpoints non-ZDR, so a wrong DB row appears as a mismatch between the row and the served policy rather than as a ZDR leak.
- **Free variants**: all-zero pricing; correct data policy per variant. Parameter counts are raw integers, not billions. A `:free` slug also depends on the **provider's own listing**: upstream matching keys free-variant endpoints off the provider's `is_free` flag, so a listing that doesn't mark the model free can leave the `:free` endpoint unmatched, diffed as removed, and auto-hidden. Whether that fires depends on the free/paid endpoint shape — during the Ling launch it didn't, and nobody could say why, which is its own reason not to bet a launch on it. For a time-limited promotion, prefer the **standard slug at $0**: the price simply rises later, with nobody to migrate off a free slug. A wrong provider `is_free` flag is a provider fix to chase, not something to route around (Ling 3.0 Flash on Novita).
- **`~latest` families**: the alias resolves to the newest eligible member, so it repoints automatically at unhide. Aliases are compatibility contracts — repointing to a pricier model is a silent price increase for alias users; skipping a new alias is often the right call. Alias URLs keep the literal `~`; after every membership/visibility/privacy change, send a real request through the alias and confirm the concrete target before proceeding. Treat mixed private/public group membership as high risk — alias resolution for public requesters hasn't been conclusively verified in every state.
- **Runtime variants** (`-pro` etc.): same upstream model ID and pricing as the base; the difference lives in routing/adapter code, not catalog metadata. Variant descriptions link the base and state only what differs.
- **Reasoning config**: mandatory ≠ default-on; never advertise effort levels (`none`, `xhigh`) unless the upstream mapping is confirmed to work. Test every advertised level per endpoint (Buddy's reasoning-effort script — the model's actual level set, not the script's default pair), with the 1P endpoint as reference; third-party endpoints can fail monotonicity even when 1P passes. Verify the **off** state too, not just the levels: a provider can accept `reasoning: {enabled: false}`, ignore it, and keep reasoning — which then fails our own response validation. The thinking wire format can differ **per model within one provider**, so a working sibling proves nothing. If we have to compensate on our side, scope it to that one permaslug, tell the provider it's their defect to fix, and own the follow-up that removes our patch (Ling 3.0 Flash on Novita, #30033).
- Public resources stay hidden until launch — the one exception is the already-announced open-weight case in §4b (model slug unhidden with zero endpoints). Leave `internal_note` to humans.
- Keep launch-thread updates compact: current state, action done, one blocker, one next action. Don't restate history.

### 2a. Promo and discount comms (GTM)

Any launch that ships a free variant, $0 or discounted rates, or a time-limited promo period is a GTM event, not just a pricing config. Loop the GTM team in **before** launch so they can brief our top apps and customers, who often want to promote it themselves or adjust their routing config to take advantage.

- Usually the promo is already known from the launch thread, so this is not a question to ask on every model. The check is the other direction: whoever spots promo pricing while staging or reviewing (`discount_to_user`, all-zero pricing, a `:free` variant, a stated promo window) flags it in the launch thread and names GTM, even when nobody raised it.
- Share the terms: which models and endpoints, the discounted and list rates, the start and end date.
- Embargo still binds. GTM gets the internal heads-up on our timeline; external customer notice waits for whatever the lab's announcement and NDA terms allow. If the terms are unclear, that is a human decision, not an agent's.
- The reversion is also customer-visible: flag it to GTM with the same reminder that schedules the price change back to list.

### 2b. ZDR and in-region-routing (IRR) endpoint variants

Retention (ZDR) and region (IRR) are two independent properties, and a launch can ship any combination of them. Stage and verify each variant as its own endpoint, and keep a variant matrix in the launch thread before the first write: standard, ZDR, US IRR, EU IRR, region + ZDR, private BYOK-only ZDR. Per row: permaslug, upstream model ID, effective provider identity (the public tag), intended credential/account, `provider_region`, `baseUrl`, effective data policy, pricing version, hidden/private/BYOK flags and grants, any required per-request parameter, baseline-test result, real-request result, and the reason for anything deferred.

**ZDR is a credential path plus an effective policy — never a label.** A `/zdr` slug or a "(ZDR)" display name proves nothing on its own.

- **The provider-side account is a prerequisite, not a detail.** Separate routing rules usually mean a separate org/account in the provider's dashboard plus a ZDR API key generated inside it. Confirm the account exists, its ZDR terms are agreed, and the key is in hand **before** any staging or code work starts — a launch cannot be finished around a missing ZDR account, and the same applies to a region-restricted account when the provider gates in-region routing that way.
- A provider's ZDR workspace is usually the same provider row and the same adapter (identical API surface). The per-provider key getter selects `<PROVIDER>_ZDR_API_KEY` from the endpoint's *effective data policy* — it branches on `isZdrEndpoint` (`packages/db/endpoints/zdr.ts`, i.e. resolved `retains_prompts: false`), not on the slug or the region. The policy override is therefore what routes traffic onto the ZDR account: a row labelled `/zdr`, or a regional row that used to get the ZDR key from its region alone, silently serves on the ordinary key until `retains_prompts: false` is set on it. Set the override and re-read the resolved policy before unhiding. Only add a provider row if the API surface genuinely differs.
- That key getter must be merged **and deployed** before anything is unhidden. The standing failure mode is an endpoint labeled ZDR that routes through the ordinary account. Staging hidden alongside the code PR is fine; unhiding is not.
- The key must be in the env schema/mocks/manifest, provisioned, **and** synced to the runtime — provisioned in Infisical is not synced to Cloudflare. A live request cannot reveal which secret it used, so the credential branch plus its tests is the guarantee: say that explicitly rather than treating a 200 as proof of ZDR.
- Effective policy: set `override_datapolicy_id`, then re-read the *resolved* policy and require `retains_prompts: false` (and training/publish false). The override ID alone is not the answer.
- A provider's ZDR coverage is often narrower than its model list — stateless chat/embeddings/OCR/audio in, agents/conversations/files/batch out. Anything served outside the normal endpoint adapter path (a hardcoded plugin route like Mistral OCR) cannot be made ZDR by creating an endpoint row; flag it instead of staging it.
- A per-request opt-out parameter some providers require for ZDR (e.g. Deepgram's `mip_opt_out`) has to be sent by the adapter on every request, with test coverage. An endpoint row does not carry it.
- Don't inherit the sibling's capacity limits without confirming capacity on the ZDR account, and reconcile `discount_to_user` against the non-ZDR sibling — report the difference rather than copying it silently.

**IRR is region: `provider_region`, plus a regional `baseUrl` when the provider has regional hosts.** Users reach it through the regional API host, not by pinning a provider slug, so a green request from the global origin proves nothing about routing — test from the intended origin. Regional upstream model IDs are frequently region-only and absent from global listings; take them from the provider's regional docs and price each region independently (a regional surcharge applies to cache SKUs too).

**Effective identity must be unique per model + variant, and regional rows get no slug override.** `provider_region` derives the public tag (`mistral/eu`, `mistral/us`); the ZDR key comes from the effective data policy, not from the region. A stored override beats derivation, so `provider_overrides.slug: <provider>/zdr` on a regional row makes it claim the ZDR identity and starves the real ZDR endpoint. Non-regional ZDR rows do need the `/zdr` override — it is their public tag.

- Before a batch unhide, compute the effective identity of every row in the batch and confirm uniqueness. The duplicate gate compares only against *visible* rows, so two hidden siblings both pass the dry run, the first one applied takes the slot, and its sibling then fails `duplicate_variant_under_same_model`.
- Fixing identity: the PATCH replaces the whole `provider_overrides` object — remove only `slug`, preserving `baseUrl` and `pricingStrategy`. Prefer removing an override to swapping in another one.
- Public tags are derived at read time and read replicas lag minutes behind a correct write. Re-check before re-editing; never edit against a stale public read.
- Before changing an endpoint's public slug, check whether traffic pinned the old one (generations' provider preferences) and report the count.
- Provider monitors that diff against a *global* provider listing can auto-hide valid regional-only endpoints. Know the mitigation and its tradeoff before launch, not after the endpoint disappears.

**Reading baseline-unhide output.** With `apply: false` a passing run now returns `status: dry_run_passed`; `succeeded` means a row was actually unhidden, and `blocked` means there is something to act on. Read `blockedDetails`, where each blocker carries its category and next action, and treat `identityCollisionSiblingEndpointIds` as a warning rather than a blocker: it names hidden siblings sharing this row's effective identity, so unhiding more than one of them will fail the duplicate gate. Sort blockers into four buckets and treat them differently:

1. **Real defect** — an adapter/serialization bug (e.g. `temperature: 0` serialized without its paired field). Fix in code, deploy, rerun; not an endpoint-record problem.
2. **Policy exclusion** — `endpoint_in_ignored_provider_models`. A product call on whether that exact upstream ID should be routable at all; retired or alias-only models stay hidden.
3. **Automation gap** — `unsupported_modality_or_no_baseline_tests` (embeddings, TTS, STT). Run Mission Control's modality-specific test templates, then the human-gated force unhide. Never bypass a missing suite through the API.
4. **Data integrity** — `missing_pricing`, `zero_pricing`, `endpoint_deprecated`, `duplicate_variant_under_same_model`. The endpoint record is wrong or incomplete; fix the row, not the code.

A content assertion that fails once and passes on rerun is nondeterminism; failing twice is real. Give the human a finish order per bucket instead of pushing every blocked row down the same path.

**Private / BYOK-only ZDR endpoints.** Mirror the model's own standard first-party endpoint — upstream ID, token limits, variant, params, features, overrides, pricing — and never the batch variant or a `-pro` permaslug. The deltas are `is_private`, `is_byok_only`, the ZDR policy override, `hidden: true` until a human verifies, and the access grant. Build them on the provider the customer's traffic actually targets: Bedrock-bound BYOK traffic needs private Bedrock endpoints, and a private Anthropic endpoint cannot serve it. Grants are a full replacement (§3). If a private endpoint exists but isn't being selected, check the org's provider settings and guardrail rows (e.g. "first-party Anthropic disabled") before suspecting the endpoint.

## 3. Verify before launch

- **Baseline-unhide ≠ the manual unhide button**: baseline unhide is a system of checks (pricing present, capability tests, usage validation); the manual button is an override that skips all of it — "ran the tests, then clicked unhide" has shipped endpoints without pricing. For license-gated launches, add the model to the auto-unhide exclusion list and block provider-dashboard self-serve unhide.
- Baseline-unhide + capability-test automations per endpoint (dry-run first), then one real request each; confirm response and billing SKUs. Reproduce a baseline failure standalone before blaming the provider — suite-order artifacts happen.
- **Mission Control test buttons are not the prod path** — after setting DB param levers, verify with a real request through the actual API, not only the endpoint test button.
- **Scope launch-week adapter fixes** to the affected permaslug/endpoint — an adapter-wide change touches other models' traffic — and tell the provider so they fix their side. **HTTP 200 is not readiness**: pre-rollout, a hidden endpoint can return 200 + a stream start but zero completion tokens — require a validated real completion (Buddy's read-only test route works on hidden endpoints).
- Eyeball the Mission Control model page: description, pricing, params, context length. New author → check the icon (Devin fixes via a code PR).
- Frontier: code PR merged **and deployed**; DB param levers set.
- Never take the model's self-description as capability proof (models hallucinate their own features); test the API directly.
- **Prod e2e before public release**: mark the model + endpoint private and unhidden, with explicit access grants (there is no automatic staff bypass — and grants are a **full replacement**, not additive: every update must resend the complete user/org list), then run real requests in prod and reconcile billing to the cent. **Buddy owns the grant itself** — his skills carry the internal org id he grants for staff testing, so a Devin→Buddy handoff does not supply the entity list and shouldn't ask a human for one; name a non-default grantee only when the testers are outside that org. Gotchas: new private endpoints may default to BYOK-only (must be off for platform-key routing); a granted key's success doesn't prove public access. A private-but-unhidden model makes GA a *privacy* transition, riskier than a visibility flip — write a state matrix: current / pre-GA / GA state per resource, exact flip order, rollback per step. Once an endpoint has been unhidden — even privately — its `is_private`, `variant`, and `service_tier` are frozen for the life of that id (hiding it again does not unfreeze them), so the endpoint side of this transition is a duplication (Buddy `POST /endpoint/{endpointId}/duplicate` or Mission Control's duplicate dialog), not a flag flip; the clone starts hidden and unexposed, so it is fully editable until you unhide it. Duplication never touches the source, so GA is a *replacement*: both rows exist, and the private test endpoint keeps serving its grantees until you retire it. Give the source its own row in the state matrix and sequence it **clone-first**: unhide the public clone, flip the model public, validate with an ungranted request, then hide the private source — public routing needs the model *and* the endpoint non-private, so no ungranted request can resolve the model until the model flip lands, and the endpoint's exposure alone proves nothing. The public uniqueness index is partial on non-private rows, so the source and its clone coexist without fighting for a slot, and this ordering keeps the model routable throughout — hiding the source first would leave nothing to route for the whole drain. That exposure step can't be a baseline-unhide: the duplicate gate counts every non-hidden endpoint for the same provider + permaslug + variant as a visible duplicate (private ones included) and privacy is not one of its identity discriminators, so a clone differing from its source only in `is_private` derives the same slug and is blocked while the source is still unhidden. Gather the baseline evidence deliberately instead — capability/baseline automations plus a validated real completion against the still-hidden clone (Buddy's read-only test route works on hidden endpoints), and pricing confirmed present — then expose it with the manual unhide, which skips every one of those checks. Once the source is hidden it stops counting as a duplicate, so later endpoints on the model go back through the normal gate. Hiding isn't instant: pinned/cached routing can keep hitting the hidden source for hours (same drain caveat as post-launch below), so the identity cutover counts as complete only once Datadog shows source traffic drained, and until then granted testers can reach either identity. That overlap is the bounded cost of not taking an outage — acceptable unless it would corrupt what you're measuring, in which case drop the source's grants as you hide it. Rollback keeps the same availability-first shape, reversed: unhide the source, re-privatize the model, hide the clone, and verify the clone drains. Otherwise keep the source's grants: they live in `private_endpoint_access` keyed by endpoint id, so they never follow the clone, hiding the source ends its routing without deleting them, and leaving them in place keeps rollback a single unhide.
- **Capability metadata is validated at write time**: Buddy's endpoint create/update routes reject `supported_video_parameters` / `supported_image_parameters` / `supported_tts_parameters` values that fail the serving schemas (the read path nulls the whole capability object on any bad value, so the endpoint silently advertises nothing — the Seedance 2.5 failure mode). A rejection means the adapter's declared capabilities and the staged metadata disagree: fix the adapter or the payload, don't retry with the field dropped.
- **Token-billed video models** (provider reports usage after completion): follow `packages/pricing/strategies/seedance/AGENTS.md` — estimate and provider-reported quantity share one SKU, last write wins, DO payloads stay JSON-primitive-safe. Add the reducer regression test before launch.

### 3a. Marketplace previews (image, video, speech)

Any model whose **output** modalities include image, video, or speech needs curated `model_examples` art.

**Where:** Mission Control → model editor → model preview, or the launch thread. Nothing public renders until a human **approves**.

**Generate:**
1. Open **Generate** on the preview card. The dialog pre-fills modality defaults — shared default prompt, `16:9` when the endpoint advertises it (else the closest landscape / sensible fallback), highest resolution tier when tiers exist, shortest video duration of at least 5s when offered (else the longest available option), and the other controls derived from endpoint-supported parameters (including provider-unique ones). Edit if the defaults undersell the model.
2. Generate → review the pending row → **Approve** → **Make primary** (or approve-and-primary). Marketplace cards / OG thumbnails and playground seeding use the approved primary for that modality.
3. Repeat per relevant output modality (image, video, and/or speech). Multi-modality models need a primary per modality you want public surfaces to show — don't assume one image covers speech or video.
4. Optional second pass: capability showcase (image-to-image, provider-specific parameters, etc.).

**Agent-generated (image, video):** an agent holding the buddy or admin key produces the same pending row without the dialog via the internal model-examples batch routes (published in `/api/v1/internal/model-examples/openapi.json`; the call-by-call recipe lives in the `buddy-handoff` skill), which is how a handoff gets art outside working hours. These batch routes are for routine/bulk example refresh — they never substitute for the §3b launch gate.

When Buddy generated the example it posts the media in the thread and applies your answer via `POST /buddy-api/model-example/{exampleId}/approve` (`make_primary` defaults to true) or `.../reject`. Unpublishing an approved example stays a Mission Control operation.

**Author flagship (`/discover` carousels):** Required when this launch is a **new author** on the platform **or** that author's **first model in a new carousel modality** (image, video, or speech). Use the flagship toggle on the same Preview card to designate this model as the author's flagship. Skip when the author already has a better flagship in that modality and this launch is a mid-tier / free / regional add-on — don't overwrite a stronger pick without an explicit product call.

### 3b. Final launch gate (image / video models) — Buddy featured-example run

For any model whose output modalities include image or video, the last step before flipping public is a real generation submitted by Buddy **directly against the public OpenRouter API** with Buddy's `OPENROUTER_API_KEY` — the exact bytes a customer sends, not Mission Control's provider-direct test buttons and not an internal proxy.

The contract (step-by-step mechanics live in Buddy's own skills, not here):

- **Preconditions**: model + endpoint staged, private + unhidden, Buddy's key's org granted access (§3), pricing + billing checks green. Buddy verifies it holds the required key **before** starting the gate and fails fast naming the missing credential — a gate must never begin on an unverified credential assumption.
- **Video**: Buddy builds the request via `POST /buddy-api/video-example/request`, submits it verbatim to the public `POST /api/v1/videos`, polls the public job until settled, and persists via `POST /buddy-api/video-example/finalize`. **Image**: same shape — `POST /buddy-api/image-example/request`, submit verbatim to public `POST /api/v1/images`, then `POST /buddy-api/image-example/finalize` with the response body + `X-Generation-Id` (images settle in one HTTP response; no poll). The legacy one-shot `POST /buddy-api/image-example` is removed; request + finalize is the only image path. Its request-level dedupe (same prompt + params returned the existing example unless `force`) went with it — finalize only dedupes by `generation_id`, so two submissions of the same payload are two paid generations. The approval gate is the safeguard: a second generation needs a new approval.
- **Pass criteria**: successful public response, non-null `usage.cost` matching expected pricing (for token-billed models, confirm the provider-reported quantity landed — generation record, not just the estimate), and a `generation_id` (`X-Generation-Id` for images; job body for video).
- Submission (and video job reads) must use Buddy's **`OPENROUTER_API_KEY`**, which must be the **same billable key** cfw-internal's `MODEL_EXAMPLES_API_KEY` is configured with — job/generation reads are scoped to the submitting key, so a mismatch makes the video finalize poll and clip download 404 after a paid generation.
- The result is a **pending** `model_examples` row plus the public CDN media URL on the finalize response (`media_url`, `thumbnail_url`, `media_type`, `mission_control_url`). Buddy posts the media, a human answers, Buddy applies it (§3a) before §4.
- Any phase failure (validation, submission, poll timeout, empty output, storage) is a launch blocker with a concrete error — do not fall back to provider-direct testing as evidence, and do not substitute the internal batch generation routes (§3a agent path) for this gate.
- **Paid example/e2e generations are strictly Buddy's.** A Devin-run generation bills real money but produces no `model_examples` row and does not satisfy this gate — Devin never submits one.
- **`sku_items` billing readback is not Buddy's.** The per-generation SKU breakdown lives behind the admin/OIDC-gated ops routes (`/api/v1/internal/ops/generation`), which Buddy's key cannot reach. Buddy verifies `usage.cost` from the public response; SKU-level reconciliation (discounts, cache SKUs, provider-reported quantities) is Devin's or a human's, via the ops route or ClickHouse.

## 4. Launch

**Readiness is not authorization**: an endpoint can be technically hittable while the provider's rollout says "tomorrow" (or only certain variants today) — reconfirm the authorized provider/region/variant scope right before unhide, release only that scope, and re-hide if provider guidance changes. First-party launches first; a lagging Azure/regional provider shouldn't extend the launch indefinitely — define a stop condition.

At the launch point, for each launching model, reset `created_at` to now immediately before or after the public visibility flip, not days earlier during staging. `created_at` drives the public "Newest" sort on openrouter.ai, so a model staged days early launches buried. The Discord RSS feed notification uses the same recency, so it does not announce the model until the reset happens.

Use either the **Reset to Now** button in the Mission Control model editor, or Buddy's `reset-created-at` action: `POST /api/v1/internal/buddy/model/{author}/{modelSlug}/reset-created-at` in `services/cfw-internal`. Buddy previews the current and new `created_at` and writes only after an explicit human-approved `apply: true`. Buddy must never self-apply this action. A human acknowledges each model. Both paths use the same query and post the same Slack notification, so the write is not silent.

At the confirmed time (wait for the lab's public announcement): release in Mission Control, with a fresh preview + approval for the visibility/privacy change itself. Privacy and hidden are separate flags on **both** the model and the endpoint, AND-gated for public routing. Order: **endpoints first, model last** (avoids a window where the slug resolves but has no available endpoints).

Verify: the definitive public check is an unauthenticated `GET /api/v1/models/{author}/{slug}/endpoints` returning the endpoint with correct pricing. Aggregate marketplace lists lag — don't read absence there as failure, but if it persists ~15 min, re-check the flags. Run a canary from a **non-granted** account and confirm: concrete provider routing, meaningful output (not just HTTP 200), the charged SKU, and expected cost. If routing/output/billing is wrong, hide the affected endpoint first, debug second. For image / video / speech models: model page card shows the approved primary, and a new-author or new-modality flagship appears on `/discover` with art (blank carousel slot = missed §3a).

### 4b. Already-announced models: unhide the slug early with zero endpoints

When a model is **already public** — the lab announced it (socials, release blog) *and* the weights/model card are published on HuggingFace — unhide the model slug as soon as it's staged and verified, even before we have a single unhidden endpoint. A model with no unhidden endpoints routes nothing, and publishing the slug early lets self-serve providers stage and launch their own endpoints against it without waiting on us (their first endpoint still requires a manual human unhide — see the provider gate in `packages/provider-monitors`). This is how DeepInfra shipped the first fully self-serve endpoint on the platform.

The public-announcement gate is hard: **never unhide a model the lab hasn't publicly announced yet**, no matter how ready our staging is — an unannounced slug on the marketplace leaks the launch, and "we only unhid the model, not the endpoints" is not cover. If a pre-announcement model must be reachable (prod e2e, partner testing), make it **private** and unhidden with explicit grants per §3, never public-unhidden.

## 5. Social media

**OG image gate, every launching model:** the launch tweet is usually the very first fetch of a brand-new model page, the OG image renders on demand rather than being pre-generated, and the crawler caches whatever it gets — so an imageless card sticks. Do this only after the model is unhidden. Unhide triggers the KV refresh; warming earlier can cache a card built from stale data. Before anything is posted, fetch the public model page, extract its `og:image` URL, fetch that URL, and require all three: HTTP 200, an image content type, and the real model card, not the generic brand fallback served when model or endpoint data was unavailable in time. On any failure, wait 5 minutes and repeat, reporting the failing state each cycle. Social is clear only when every launching model passes. The OG URL contains a build hash, so a `projects/web` deploy between the check and the post invalidates the warmed image and requires a re-run. PR #33559 capped the crawler-facing lookup and made complete cards CDN-cacheable, but the first crawl of a brand-new model is still cold.

- Ping Buddy with the provider's launch language and ask for a Typefully draft. It returns edit + preview links.
- Iterate in the thread; decide single post vs. thread, handle tagging. One link per X post (each model page gets its own preview card); put the free-tier training disclosure next to the free link, not buried in the main post. Sign-off before scheduling.
- A factual correction in social copy (wrong context length etc.) often means the catalog has the same error — audit every system of record, not just the tweet.
- Editorializing adjectives get quoted back — every characterization must trace to the lab's own launch language; when in doubt, quote them.
- Copy must match the launch state at post time, not the plan from hours earlier — don't say "live" while private/hidden; re-check state right before publishing. Use the provider's own positioning language and tag the partner mid-sentence. Alias links use the canonical `~` URL.
- **Never pre-empt the lab's announcement** — post only after theirs is live. Drafting is not publishing — Buddy holds drafts until explicitly told to schedule/post.

## 6. Post-launch monitoring (Datadog)

For the first hours after unhide:
- Watch request volume, error rate, latency/TTFT, routing distribution, and upstream status codes for the new endpoints in Datadog (Devin's `debug-prod` skill can pull targeted queries).
- Common early failures: wrong upstream model ID, missing prod API key, zero-token "successes", billing at $0 or the wrong rate, params forwarded that the model now 400s on.
- Hide a failing endpoint rather than letting errors accumulate; escalate in the launch thread. Hiding isn't instant — pinned/cached routing can keep hitting a hidden endpoint for hours; verify the drain in Datadog.
- **Provider migrations leave zombies**: when moving endpoints to a new provider, "hide the old endpoints" needs an owner and a follow-up, or both sets serve indefinitely.
- Sweep leftover follow-ups: held regional endpoints, pricing reversion reminder, remaining data-policy or cache SKUs.

## Who does what

**Proceed inside the boundary, stop at its edge.** Once a step's standing approval is granted, the owner executes it to completion without re-asking. Stop and escalate only at a genuinely new write, a changed payload, a failed precondition, or a missing credential.

Devin can also talk to Buddy directly in Slack (agent-to-agent) — but only when a human explicitly asks for it (e.g. "Devin, can you drive Buddy"; see the `buddy-handoff` skill). Default is human-in-the-loop: the human relays between agents and clicks every approval gate — an agent handoff never substitutes for your approval.

## Troubleshooting

- **Rule out admin-surface failures before touching model state**: an MC deploy/SSR crash can render stored config (e.g. grants) as missing, and an R2 credential failure can fail a step after a successful paid generation. Read the state through the API before re-staging, re-granting, or flipping privacy — the DB state usually survived.
