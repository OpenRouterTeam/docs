Moving SSE merge out of adapter post-mortem ([bug discussion here](https://openrouter.slack.com/archives/C05F41UHEE7/p1744150307301399)):

There were two user-facing issues:
1. Tool calls: the SSE merge was changed to use the `getCompletion(output: OutputUnion)` function to extract text completion, in an effort to consolidate our logic for doing so. However that function is more oriented toward accounting purposes where we want to interpolate the tool calls into the full completion string, while for SSE merging we handle tool call merging separately.
2. One user (Magai) had been sending us streaming requests, but with `stream: "true"` (i.e. the string `"true"`) instead of a boolean. Previously this had been working by accident because the string `"true"` is truthy. This PR enforced that the `stream` field, if present, must be a boolean. This caused the user to receive 400s for those requests.
When the user initially reported issue (1) there was some confusion over what kind of requests they were making. The upstream Claude 3.7 does not handle `response_format: { type: 'json_object' }`  correctly and returns a Markdown code block (starting with "```json"), and this failure was consistent when E2E tested against the code before and after the merge so I initially thought this was an upstream change. After we received the Magai bug report we performed a rollback, and from their later more detailed report we found issue (2) and fixed it via coercing `"true"/"false"` to booleans. Further investigation of the tool calling issue allowed us to create a reproduction and fix issue (1).

Opportunities for improvement:
• For issue (1), there was a test case for tool merging but it did not check what the text completion string was, only that the tool call field was correct. The test was changed to check all fields of the response when merging tool calls to catch any future regressions.
• We suppress logs/metrics around 400 responses aggressively; they don't show in almost any part of our dashboards. We should at least have some metrics surfaced around these, and possibly some outlier detection so we can notice if code changes cause errant 400s.
