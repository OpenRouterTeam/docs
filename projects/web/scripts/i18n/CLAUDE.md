# Translation CLI

Operating the pipeline (adding copy, locales, terms, running translation, checks, the eval, and handling failed runs or bad-translation reports) is covered step by step in [RUNBOOK.md](./RUNBOOK.md). This file explains the design and the rules behind it.

Git owns translation review and release history. Do not add approval-status sidecars, a translation database, or a separate publish service.

## Workflow

From `projects/web`:

```bash
bun run i18n:extract
bun run i18n:translate --locale es --dry-run
bun run i18n:translate --locale es
bun run i18n:check
git diff -- i18n/gt/messages
```

Contributors add copy with `<T>`, `useGT()` or `getGT()` and changed-file lint enforces coverage. Run `i18n:extract` locally (no secrets needed) and commit the regenerated source catalog and sidecar with the copy change. Translations for the other locales are generated by a separate translation job and are not required for a feature PR or for the build to pass. Running `i18n:translate` locally is optional.

The `bun run x` wrappers load the normal development environment. In a credential-free CI environment, invoke the same TypeScript entrypoints directly with Bun: `bun scripts/i18n/extract.ts --check` and `bun scripts/i18n/translate.ts --check`. Neither performs translation or requires a model key. To use an already exported `OPENROUTER_API_KEY`, invoke `bun projects/web/scripts/i18n/translate.ts` from the repository root directly: the `bun run x` wrapper can replace it with the development Infisical value. Never print the key to diagnose authentication. HTTP 401 means the selected key is invalid, 402 means balance is unavailable, and 404 with required parameters means the selected model/provider cannot serve the requested configuration. The web build does not run any i18n check.

The check has two modes, and both require fresh extraction to match the committed source catalog and sidecar (`run i18n:extract`). Strict mode (`extract.ts --check`, `translate.ts --check`, `bun run i18n:check`, `i18n:validate`) is for translation PRs and the translation job: every target catalog must also be complete, fresh, on-policy, within `maxChars` and glossary-consistent. Allow-gaps mode (`extract.ts --check --allow-gaps`, not run by any CI job, the build or a deploy) writes nothing and fails only when a committed translation exists and is invalid (structure, placeholders, ICU, whitespace, code-element text, `maxChars`, terminology, glossary pinning, semantic safety of risk-tagged entries); it tolerates missing translations, stale fingerprints, orphaned entries and a locale file that does not exist yet, logging only per-locale counts (`locale`, `missing`, `stale`, `orphaned`, `total_source`). Both modes share `checkCommittedLocale` in `check-committed-locale.ts`; do not weaken strict mode to make allow-gaps mode pass.

`extract` runs pinned `gt generate` into temporary files and updates only the source catalog and its metadata sidecar `messages/en-US.meta.json` (per hash: `id`, `context`, `maxChars`, `filePaths` as GT recorded them). The sidecar is translation input only: the runtime catalog shape and values are unchanged, a missing sidecar means no metadata, and a malformed one aborts the run. `maxChars` is both rendered into the prompt and enforced on the reply (Unicode code points of the translated segments joined, placeholder tokens counted as written), so an over-long entry is rejected and retried like any other invalid entry. The same measure applies to what is already committed: a reusable translation over its current limit is dropped and sent again, `--check` fails on it, and an over-long glossary override is reported as an error rather than retranslated, since the glossary pins it. Never run bare `gt generate` against the committed output directory: it seeds untranslated target entries with source text, which is indistinguishable from an intentional unchanged translation in a Git-owned workflow.

`translate` retains every present valid translation whose recorded source fingerprint still matches, including source-equal text. GT's lookup hash omits some JSX fields, so `messages/<locale>.source-hashes.json` records a SHA-256 fingerprint of each complete, canonical source entry, together with its glossary pin when one exists, when that locale is written. Attribute/tag edits therefore retrigger translation even when the GT key is unchanged, and a glossary edit retriggers only the entries it pins. The sidecar's `policy` field records three fingerprints of the locale's translation policy, `prompt` (the system prompt in `openrouter-leaf-translator.ts`), `globalContext` (the committed `context/global.md`) and `localeContext` (`context/<locale>.md`), each over trimmed text. A policy mismatch does not make source-fresh translations stale: `translate` keeps them, logs the changed components and rewrites the sidecar under the current policy, `--check` fails until that rewrite is committed, and `--force` regenerates the locale when the new guidance should be applied to existing copy. A sidecar written before the split records a single string and is read as an unknown policy: its unpinned entries stay fresh by source alone, its glossary-pinned entries read as stale because their fingerprints did not include the pin, and the next writing run re-pins them from the glossary without a model request and records the current policy. One-off CLI inputs such as `--context-file` are not part of the policy. Missing provenance is treated as needing translation, never silently blessed. These files are freshness metadata, not approval states or a lint baseline.

The CLI translates missing/stale entries, validates model output, reusable entries, and exact glossary overrides, then writes locale files. Every entry that validates is persisted; an entry whose model reply is still invalid after the single-entry retry (or whose request failed) is left absent from the catalog and from its source fingerprints, so it stays pending. Entries the limiter never sent (request cap reached, cancellation, or an earlier authentication/balance failure) are deferred: also absent and pending, but counted per locale rather than listed per entry. The CLI then reports each remaining failure (locale, entry hash, reason), logs the deferred count per locale, and exits non-zero whenever anything is still missing, so a rerun only translates what is still missing and converges. `--check` still requires complete catalogs. Model replies with accidental leading/trailing whitespace adopt the source leaf's edge whitespace before validation; every other mismatch is rejected, as is any control, zero-width, bidi-format or byte-order-mark character the source leaf does not itself contain (tab, newline and carriage return stay allowed). When a batch reply is rejected, the entries in it that validate on their own are kept and only the rest are retried one at a time, with an instruction naming every placeholder and tag to keep. An entry that still fails gets one last joined retry, where a run of text leaves separated only by inline elements is translated as one sentence and split back on markers; `INLINE_TAGS` in `gt-text-leaves.ts` decides which elements count as inline, so add any new inline component used inside `<T>` there or its entries skip that retry and simply stay pending. Writes are atomic per file, and each locale is written as soon as it finishes, so a later locale's failure or cancellation does not discard an earlier locale's progress. Each catalog is written before its source fingerprints, so a partial failure cannot mark an old catalog fresh. Inspect the Git diff after any failure. The per-locale catalog is the only checkpoint; there is no separate publication phase, and a failed job is rerun.

`validate` checks committed catalogs against the extracted source. `check` also performs fresh extraction in scratch space and fails on source drift. Both reject missing/stale keys, changed GT structure, invalid placeholders, and glossary/catalog disagreement. These checks are not linguistic evaluation or proof that prose was translated: Git review owns meaning and intentional source-equal output. The repository's translation-copy lint owns unwrapped-copy coverage separately.

## Translation-copy guards (PR 2)

PR 2 is one PR for guards, reporting, and changed-file enforcement. It does not bulk-wrap UI, generate translations, weaken source/catalog validation, change legal copy, or alter the 40-entry/32-concurrent translation defaults.

From the repository root:

```bash
bun run i18n:coverage
bun run i18n:coverage:report
```

CI/PR enforcement uses the existing changed-file oxlint path through `bun run lint`/`bun run verify`. It checks all display copy in each selected file, not only modified lines. Exact-name display copy has no baseline or grandfathered allowance. Two count-pinned baselines exist for the heuristic rules only, `scripts/oxlint/translation-copy-suffix-baseline.ts` (suffix-matched display names such as `searchPlaceholder`) and `scripts/oxlint/no-edge-variable-in-t-baseline.ts` (`<T>` blocks that start or end with a variable). Each pins a file to its audited count, so any net-new finding in a listed file and every finding in an unlisted file is reported. A count baseline cannot tell a replaced finding from the original one it replaced, which is why the counts only go down: never add an entry or raise a count, and lower or delete entries as files migrate. There is no pruning command or separate whole-project CI gate.

The commands above are explicit, credential-free full-project scans of the same translation rules. `i18n:coverage` emits normal diagnostics; `i18n:coverage:report` emits oxlint JSON including file/line locations. Both return a nonzero exit status when violations exist. They never invoke GT generation, a model, or a translation service.

Scope is production JS/TS/JSX/TSX in `projects/web`, `packages/frontend`, and `packages/frontend-utils`, including public pages and authenticated UI. Mission Control, workers, generated output, tests, stories, and scripts are not translation targets. Web legal-document owners under `(static)/(legal)/terms`, `privacy`, and `terms-of-service-enterprise` stay English. This does not exempt ordinary privacy settings, terms links, or surrounding product controls. Mintlify/MDX requires its later adapter and is not silently counted as covered here.

The AST guard detects JSX text and literal expressions; conditional/template copy; display/accessibility props; display-valued configuration fields; local literal bindings rendered in display positions; shared label defaults; and toast/notification/alert/confirm copy. A real imported GT `<T>` owns child copy, GT `Branch`/`Plural` variants, and the supported HTML text attributes (`placeholder`, `title`, `alt`, `aria-label`); arbitrary component props and render callbacks still need their own helper. Import bindings and lexical shadowing are resolved using oxlint's scope graph. Import `T` under its original name: the pinned extractor silently omits renamed `T` imports, so the extractability rule rejects them. GT translator/registration calls must use static strings or the imported `derive` helper, with dynamic values in placeholders. Fresh extraction remains the authority on whether `derive` expressions actually resolve.

PR 3 must run the full translation check and full oxlint check over web/shared frontend, not just changed-file CI. Fix all findings in scope; classify genuine false positives or intentional exclusions with narrow, reviewed reasons. Do not hide remaining findings behind a new baseline or broad disables. Required migration checks from the repository root:

```bash
bun run i18n:coverage
bunx oxlint --config oxlint.config.ts projects/web packages/frontend packages/frontend-utils
bun run verify
```

The lint report can find raw strings before migration. GT catalog extraction is a separate step: it only extracts supported GT helpers such as `T`, `gt()`, and `msg`/`derive` patterns. PR 3 uses full lint findings to wrap the strings first, then extracts and generates all intended translations through the in-house CLI. An empty or small GT source catalog is not evidence that raw copy has been covered.

Use an adjacent `i18n-exempt: legal|brand|technical|user-content -- specific reason` comment only for deliberate source-only copy. The reason must have at least ten characters; a blanket file exclusion or an unexplained disable is not a migration strategy. Keep contractual consent, policies, DPA/AUP and legal disclosures English, while translating surrounding nonlegal product UI.

Shared client components can use `T` and `useGT` from the pinned `gt-react` directly. Web's existing `gt-next` provider supplies the selected locale and committed catalogs through the same GT React context. MC supplies `EnglishTranslationProvider` at its root: locale is fixed to `en-US`, `enableI18n` is false, translations are empty, and both cache/runtime service URLs are null. No label-prop adapters are required just to support MC. GT without a provider is not an English fallback; do not catch missing-provider errors or weaken `useLocale` globally. Shared components that deliberately retain injectable English defaults may still use `i18n-exempt: source-default -- specific reason` (shared packages only).

The extraction configuration includes web and `packages/frontend`/`packages/frontend-utils`, not `projects/mission-control`. Its negative globs exclude tests, stories, generated/build output, scripts/test utilities, and the web legal-document tree; scratch extraction preserves the leading `!`. The real-executable scope fixture tests these boundaries, including `gt-react` messages in sibling packages. MC-only messages never enter a target catalog. Messages in shared packages remain in scope even when MC also consumes them; the extraction allowlist is package-based, not a reachability analysis of individual web imports. Keep MC-only copy in MC, not in shared packages.

Runtime regression tests prove the same shared `gt-react` hook renders a catalog-shaped Spanish translation (keyed with GT's `hashSource`, not read from a committed catalog) under web's provider and source English under MC's provider, including hydration and zero fetch calls. Use MC's `renderWithMissionControlLocale` helper for the real English provider in component tests. Browser proof lives in the `I18n/Mission Control English provider` story.

Static lint cannot prove the provenance of arbitrary API data, cross-module aliases, custom notification aliases, arbitrary helper return values, or MDX. The report is a migration aid, not a claim that every visible string has been found. Use real extraction, rendering tests, and a final route/component audit alongside the full scans; extend AST fixtures for any newly discovered escape before migrating it.

Local display bindings are followed through arrays, aliases, templates, `filter`, `slice`, `concat`, and `join`, including the rendered left side of `||` and `??`. Word separators passed to `join` are display copy too. Filter predicates, slice indexes, dynamic method names, and native `style`/`script` expression bodies are not display text. This does not trace arbitrary callbacks or methods; add an extraction contract fixture before extending the supported value flow.

## Pinned GT authoring contract suite

`packages/frontend` consumes `gt-react` in production shared components and declares the same pin as a runtime dependency. MC already consumes its English provider at runtime and retains a runtime dependency.

Run `bun test projects/web/scripts/i18n/translation-contract.test.ts` from the repository root. The suite uses the actual oxlint plugin and pinned GT executable, never mocked extraction or model calls. Version assertions require an explicit contract review when upgrading `gt-next@11.1.23` or `gt@2.20.0`.

The paired fixtures verify raw copy is flagged, the supported wrapped form is lint-clean, and actual extraction contains exactly the independently specified messages. The wider API matrix checks semantic text leaves and entry counts across the following families:

| API/surface | Contract |
| --- | --- |
| `T`, rich text, supported HTML text attributes | Complete structured source; custom non-GT props are not implicitly covered. |
| `useGT`, server `getGT`, callback aliases and helper/import boundaries | Expected source strings survive extraction. |
| `msg`, `useMessages`, `getMessages`, registered arrays | Registered source is present; encoded-message consumers do not duplicate it. |
| Imported `t` calls and tagged templates | Literal source is registered; interpolation becomes numbered placeholders. |
| `derive`, `Derive`, finite alternatives, imported object members, `declareVar` | Finite text choices are extracted and GT's runtime-variable encoding is preserved. |
| `Var`, `Num`, `Currency`, `DateTime`, `RelativeTime` inside `T` | Surrounding text is extracted; variable values remain structural. |
| `Plural`, all plural forms, `Branch`, ICU plural/select | Every authored variant survives. |
| IDs/context/length metadata, duplicates, HTML identifiers | Context can distinguish entries; duplicates can collapse; IDs are not translated text. |
| Locale hooks, standalone formatters, `gtFallback`, `mFallback` | No message registration is expected from these APIs. |
| `useTranslations` / `getTranslations` | Dictionary lookups author no inline source. These tests do not assert dictionary-loader support: a separate source dictionary and runtime/MC loader integration are required before adopting that API. |
| Runtime-only `Tx`, renamed `T`, dynamic call source, lookalike wrappers | Must not be mistaken for supported lint-clean build-time authoring. |

This is a coverage contract, not a numeric 1:1 invariant: several lint findings can become one rich-text/plural entry, repeated messages can deduplicate, and registration metadata can distinguish otherwise identical text. It does not claim every GT runtime API is wired into this application, nor that arbitrary programs are statically proven translatable. Dictionary loaders, generated compiler internals, other frameworks, and runtime/cloud translation are separate integrations, not inline-source coverage. Add a fixture whenever a migration introduces another supported authoring shape.

## Controls

- `--locale es` selects a configured target; omission runs all targets.
- `--dry-run` reports work without a model call or file writes.
- `--force` is the full sweep: every committed, unpinned entry with translatable text is sent again with the current prompt, context, terms and metadata, and under the default `--judge gate` the fresh candidate replaces the committed translation only when the committed one scores below the pass threshold and the candidate clears it by at least 0.1 (see below). Use it after changing the prompt, context, terms or model, then review the diff. With `--judge off` or `--judge report` it regenerates blind, so every entry changes. Exact glossary overrides still win either way.
- `--model ID` changes the model. The default is the pinned `TRANSLATION_MODEL`. Models differ in which request parameters they accept and how long a batch takes: `--reasoning-effort none|minimal|low|medium|high` (default `low`, `none` omits the reasoning field), `--temperature none|N` (default `none`, which omits it), `--max-output-tokens N|unlimited` (default 8,000), and `--timeout-seconds N` (default 60, up to 1,800) tune a run for a replacement model. A 404 with `provider.require_parameters` means the model has no endpoint for the requested combination; omit a parameter rather than dropping the requirement. Verify a replacement model with `--dry-run` and one locale before a large run.
- Guidance travels with every request in three layers, all versioned under `i18n/gt`. `context/global.md` and `context/<locale>.md` are read by default when present (global first, then locale, then any `--context-file PATH`, all counted against `--max-input-chars`). `terms/terms.json` is term-level policy: each English term has a `kind` (`protected` names stay verbatim in every locale; `product` and `marketing` terms carry a curated `form`, optional `variants`, and `forbid` list per locale), an optional `note` shown to the model verbatim, English `variants` that also trigger it, `exempt` phrases that contain a source form but name something else (`Google Workspace`, `/workspaces/`), `unless` words whose whole-word presence anywhere in an entry marks it as a different sense of the term so the rule is neither prompted nor enforced there (`GitHub`, `rotate` for a credential `token`), and an `exclusive` flag under which an accepted form may appear only where the source uses the term (so a common noun is never rendered as the `Interns` product). Rules whose English form occurs as a whole word in a batch's prose (ICU argument names such as `{workspace}` and exempt phrases are not prose) are rendered into that batch's prompt and enforced on the reply after structural validation: a reply that uses a forbidden form or lacks every accepted form is retried like a placeholder failure and, if still wrong, reported as a terminology failure. `validate`/`check` apply the same rules to committed catalogs. Entry metadata from the sidecar is rendered as per-entry hints. `i18n/gt/glossary/<locale>.json` remains the exact whole-string override for plain entries and always outranks term policy; a glossary-pinned entry is exempt from the term check.
- `--context-file PATH` adds one more guidance file for a single run, on top of the committed context files.
- Default limits are 1,024 concurrent requests across all locales, 40 entries per batch, 20,000 characters per serialized user message (locale context, entries, layouts, metadata hints and the term rules the batch triggers), 8,000 output tokens per request, and 2 transient retries. Under Bun (`bun scripts/i18n/translate.ts`, as the sync workflow runs it) `fetch` sends at most 256 requests at once unless `BUN_CONFIG_MAX_HTTP_REQUESTS` is raised, so the workflow sets it to 1024; set it yourself when running the script with Bun directly (`bun run i18n:translate` runs under Node through `tsx` and has no such cap). There is no total request cap by default: one invocation processes all pending entries. Set `--max-requests N` to opt into a request cap (up to 10,000). Override with the corresponding `--concurrency`, `--batch-size`, `--max-input-chars`, `--max-output-tokens`, `--max-requests`, and `--retries` flags. Batches are cut by that serialized length, so a longer context leaves less room for entries; a single entry whose message still exceeds the cap fails before anything is sent. Split the source message or shorten the context. The single-entry retries never exceed a cap the entry itself fit: the strict placeholder instruction is part of the system prompt, and the joined retry replaces per-segment JSON keys with shorter boundary markers, so its user message is shorter than the segmented one.
- Within one invocation a locale converges over up to `--max-passes N` passes (default 4, up to 20): entries whose batch failed validation or exhausted its transient retries are re-sent in halving batches after an exponential pause (2s, 4s, ... capped at 30s). Successful entries from earlier passes are kept. Only retryable failures re-enter a later pass: entries that were never sent (request cap, cancellation, authentication/balance failure) are deferred, and a failure the run cannot recover from (authentication/balance status, a Retry-After beyond 60s) is reported once. Both stay pending for a rerun. Cancellation cuts the pause short and starts no further pass. Passes share the request cap.
- Request caps include structural retry requests and transient retries. SDK retries are disabled so there is one retry owner; a thrown transport error (socket reset, per-request timeout) is retried like a failed request unless the run was cancelled. Respect bounded Retry-After delays; longer delays require a later rerun. Authentication/balance failures stop further scheduling. Cancellation propagates to in-flight requests; external cancellation does not remove the per-request timeout.
- These are request/payload/output-token limits, not a dollar estimate. Verify model/provider prices before raising caps. Timeout/cancellation does not guarantee the provider did not bill a request.
- `--judge off|report|gate` (default `gate`) controls the Jev pass described below. Jev requests are separate from the translation request cap and share a fixed limit of 128 in flight across all locales. At 1,024 Jev returned 529s on sync runs and a full `--force` run with all seven locales ran out of memory.

## Jev judge inside translate (paid, semantic)

Deterministic validation cannot see a dropped sentence, a garbled clause or a translated command that still has the right placeholders and tags, so `translate` asks Jev (`typesafe/jev-1.13` through `POST /api/alpha/decisions`, the same `OPENROUTER_API_KEY`) up to three Noul questions about every candidate the model produced in this run: `complete` (every sentence, clause, instruction and qualifier of the English appears), `faithful` (referents, numbers, negations, conditions, obligations and certainty are preserved) and `literal_intact` (code, commands, flags, URLs, identifiers, product and model names, placeholders and `keep_verbatim` glossary literals are unchanged). `literal_intact` is only asked when the English text mentions a protected term or carries a literal-shaped token (URL, flag, `snake_case`, `dotted.name`, `path/segment`, `key: value`, `gpt-5`, `camelCase`). Asked about plain prose, Jev reads ordinary translated words as altered literals, and an exclusive term that rides every translation batch (`Interns`) counts only when the entry mentions it. Code element text is compared deterministically by `validate`, so it is shown in the layout but not listed in `keep_verbatim`. Each `keep_verbatim` item names the English term, the locale's accepted target forms and the term's note, because Jev otherwise reads `Interns` rendered as the accepted singular `Intern` as an altered literal (in the full-catalog audit that one term produced 816 of 1,855 `literal_intact` flags; on a 130-entry Spanish sample the accepted forms and note cut the flags to 19). The state carries the target locale, the sidecar `context` as an author note, the rendered-in file paths, the resolved risk tier, the entry layout, those protected terms, the triggered term rules, and the English and translated text. `judge-questions.ts` owns the questions and the thresholds; `judge-entries.ts` sends them with bounded concurrency; `judge-candidates.ts` applies the mode.

The weakest of the probabilities asked decides: at most 0.5 is a `flag`, under 0.8 is `uncertain`, otherwise `pass`. The thresholds came from a 43-case pilot over reviewed bad and fixed translations and are provisional until the full-catalog audit below has been read; do not tighten them from a single run.

- `off` sends no Jev request.
- `report` judges the new candidates and records findings. Every deterministic-valid candidate is still written; a finding is a pointer into the diff, not a rejection.
- `gate` (default, what the sync job runs) gives a flagged candidate exactly one retry, a single-entry request with the failing criterion appended as a hint. The retry replaces the original only when it is not itself flagged; if both are flagged, the candidate whose weakest criterion scored higher is written and the entry is recorded as `review`. There is never a third request.

Without `--force`, Jev never causes a regeneration of a committed translation: entries retained by fingerprint are not judged during `translate`, and a `flag` or `review` on a new candidate does not make the entry missing, so a rerun does not translate it again. A request failure, timeout or malformed reply is recorded as `unavailable` for that entry and the candidate is kept: Jev fails open, deterministic validation fails closed. Before giving up, a Jev request that fails in transport or returns 408, 429 or a 5xx is retried up to three times with a 1s, 2s, 4s backoff (capped at 16s) or the server's `Retry-After` when longer, up to 60s. 401 and 402 stop the run's Jev requests at once, and a malformed reply is never retried. Findings carry `locale`, `hash`, `kind` (`flag`, `uncertain`, `unavailable`), the weakest `criterion` and its `probability`, `action` (`kept`, `review`) and `retried`, never text. They appear in the `--report-json` output (per-locale `judge` summary plus top-level `findings`) and the sync PR body renders them per locale under review needed, flagged but kept, uncertain and unavailable. Jev is a supplement: the ICU, placeholder, tag, code-text, whitespace, glossary, term and semantic-safety checks stay the only gate on a write, and legal or billing copy still needs a bilingual human.

### The full sweep (paid, writes)

`bun run i18n:translate --force [--locale es]` is the only way Jev leads to a committed translation being sent again. Under the default `--judge gate` it first judges every committed, unpinned entry with translatable text so each has a score to beat, then sends every one Jev could judge through the ordinary gated path with the current prompt, context, terms and metadata, and compares. The candidate replaces the committed translation only when it passed deterministic validation, Jev could judge it, it is not itself flagged after its one retry, it differs from the committed entry, the committed translation's weakest criterion scores below the pass threshold (0.8), and the candidate's weakest criterion scores at least 0.1 higher than the committed translation's (`MIN_REPLACEMENT_GAIN` in `judge-candidates.ts`). A passing committed translation is never replaced, whatever the candidate scores. The margin exists because two Jev scores of the same text differ by a few hundredths between runs: a strict `higher` rule replaced 19% of the catalog in one sweep, three quarters of it by less than 0.1, most of that lateral rewording. Otherwise the committed translation stays and the entry is recorded as `review`; a candidate that failed validation, was deferred or never arrived also leaves the committed translation in place. An entry whose committed translation Jev could not judge is left untouched and counted as `unavailable`. Missing entries are filled and orphans dropped exactly as a plain `translate` would, and a policy change on its own never triggers this sweep: without `--force` the changed components are logged and source-fresh translations are kept. Gate mode refuses `--force` without `OPENROUTER_API_KEY`, since there is nothing to compare against; `--force --judge off` regenerates blind. Because the translator is not deterministic, this rule is what lets a second sweep leave the catalog alone: an entry changes once, when a candidate is measurably better, and stops changing once it passes. `--dry-run --force` counts the entries a sweep would send. The report's `retranslation` block per locale carries `selected`, `unavailable`, `retranslated`, `replaced`, `kept` and `identical` (candidates that serialized to the committed entry again), and each decision is logged with both probabilities and no text.

## Full-catalog audit (paid, zero-write)

`bun run i18n:judge [--locale es] [--max-entries N] [--concurrency 8] [--timeout-seconds 30] [--out judge.json]` asks the same three questions with the same state about every fingerprint-fresh committed translation of every configured locale (or the one `--locale`), in hash order, skipping source-equal entries. It never writes a catalog. Run it after changing the questions, the thresholds or the translation model, or when a locale is suspected of carrying older defects; read its `flag` findings first (probability at most 0.5 on one criterion), then `uncertain`, and treat `unavailable` as a service problem rather than a translation problem. A flagged entry is fixed by editing the catalog or the glossary and reviewing the diff, by deleting the entry so the next `translate` regenerates it, or by running `translate --force` for the locale as described above; the audit itself proposes nothing and stores no approval state. `--out` writes the JSON report of summaries and hash-keyed findings with no source or target text.

## Planning dry run (paid, zero-write)

`bun run i18n:plan --locale es --since <revision> [--out PATH]` never writes a catalog. It pairs English entries removed since `--since` with the entries that replaced them (a shared explicit `id`, or the same file with token overlap at least 0.5) and asks Jev (`typesafe/jev-1.13` through `POST /api/alpha/decisions` with the same `OPENROUTER_API_KEY`) typed questions only: a Noul on whether the committed translation of the old English still renders the new English (probability at least 0.9 proposes `retain`, at most 0.5 proposes `retranslate`, otherwise `review`), a Score on how a risk-tagged translation moves the meaning, and a Choice on why a source-equal translation equals its English. Choice/Score answers with confidence under 0.6, unavailable or malformed replies, and missing answer keys are reported as failures for a human, never acted on. The output is a JSON report of proposals to compare against the deterministic tables and Git review; it is not an approval state, a translation database, or legal sign-off, and the glossary, term rules, placeholder, ICU, tag and semantic-safety checks still gate every write made by `translate`.

## Safety and maintenance

Do not log source text, translated text, raw SDK errors, or credentials. Keep request-error summaries deliberately bounded. Lock extraction and translation writers; preserve user edits detected during a run. If a killed process leaves `i18n/gt/.translation.lock`, confirm no writer is running before manually removing that exact file. Do not auto-delete another process's lock.

Manual fixes go directly into the locale file or exact-override glossary, then through `i18n:check` and normal PR review. Adding a locale requires the existing shared locale configuration, GT extraction config, runtime catalog loader, and actual reviewed catalog to agree; the existing loader/config test detects drift. Keep loader/runtime behavior out of this build-only tooling.

The model transport uses request-specific strict entry/segment ID objects and requires provider parameter support; runtime validation still owns ICU, rich-text and whitespace preservation. The default model (`openai/gpt-6-luna`) was verified live with `max_tokens`, low reasoning, and JSON schema, and rejects any `temperature` under required parameter support (HTTP 404), which is why the default omits it; `max_completion_tokens` with required parameter support was rejected. Placeholder-only GT entries are retained locally without a paid request. The model transport and request limiter are reusable without GT artifacts; a format adapter can provide its own output validator. The current CLI runner is GT-specific. Mintlify's MDX/OpenAPI extraction, source-fingerprint mapping, reconstruction and deployment remain in its integration PR. Do not add a fake `--surface docs` option before that adapter exists, and do not force arbitrary MDX through ICU validation.

## Model eval (paid)

`translation-eval.ts` compares candidate translation models on two suites: `sampled`, a fixed 96-case stratified sample of the source catalog, and `targeted`, hand-authored cases for known failure modes. It is a plain Bun script, never a `bun test` file, so ordinary test discovery cannot spend money. It needs `OPENROUTER_API_KEY`:

```bash
bun run i18n:eval                                   # all candidates, both suites
bun run i18n:eval -- --suite targeted               # only the authored regression cases
bun run i18n:eval -- --pilot 2                      # bounded smoke, not a comparison
bun run i18n:eval -- --models openai/gpt-5.6-luna --report /tmp/eval.md
bun scripts/i18n/translation-eval.ts --help         # with an already exported key
```

Every candidate request is the production request: `buildChatRequest` from the translate CLI with the same `context/` guidance, `terms/` rules and entry metadata production sends, plain non-streaming `chatSend`, strict JSON-schema `response_format`, SDK retries off, no tools. Only `max_tokens` is left unlimited so truncation cannot invalidate a result. The judge is a second plain structured-output request. Latency and cost per case come from the response, and per-model tallies keep separate denominators for request failures, deterministic gate failures, judge failures and quality misses, broken down per locale so a locale-specific regression is visible on its own row.

Gates run in order after the reply is decoded, and a case that fails one is never judged: structure (JSON shape, entry and segment IDs, ICU placeholders, edge whitespace, the production validator), terminology policy (the locale's `terms.json` rules for every term the English source mentions), authored `contains`/`forbids` checks, then cross-case `agreeWith` consistency (every case in a locale naming the same term must land on one accepted form, so a feature is not "Guardrail" in the nav and "Leitplanke" in a heading). Exit status is non-zero for any gate failure and for any request that failed, since an unanswered case proves nothing.

Sampled cases (`translation-eval-cases.json`, regenerated by `translation-eval-build-cases.ts`) hold only id, English source segments, target locale and stratum. Targeted cases (`translation-eval-targeted.json`) add an explicit `targetLocale` (the dataset test requires every configured locale to be covered), optional entry `metadata`, `checks`, `agreeWith`, and a per-case `rubric` for the judge. The parser rejects a `contains` the policy forbids or a `forbids` the policy accepts, and an `agreeWith` the policy does not resolve for that locale, so a stale case cannot silently pass. There is no reference translation on purpose: the committed catalogs were produced by an earlier default model, so grading against them favours the incumbent. Linguistic quality is an LLM-judge measurement against the English source, the locale guidance and the hand-written `translation-eval-glossary.json` (marked for native review), reported as a pass rate rather than gated. Read unequal denominators (provider rejections), judge-family overlap with a candidate, and pilot sizes as limits of the measurement before calling a winner.

## Finite display labels

Keep protocol enum values unchanged. Own translated labels in frontend presentation modules using exhaustive `msg()` maps and resolve them with `useMessages()` or `getMessages()` at every display consumer. Do not import the legacy English output-modality/use-case label APIs or the models schema's English sort map into frontend code; the copy rule rejects these imports (including named aliases and re-exports).

The copy rule follows local object lookups and synchronous helper return branches into display contexts, including `formatLabel` callbacks. It recognizes `Metric.name`, `ProviderTrustFilterSection.name`, `Tooltip.content`, and `prefixLabel`; unrelated `name` props remain machine values. These are explicit component naming contracts. New component APIs with ambiguous prop names need a reviewed contract and a positive/negative parser fixture. Local tracing does not execute imports, evaluate callback arguments, or infer the language of runtime values. Imported APIs need explicit restrictions, and rendered enum labels need locale tests that also assert stable submitted values.
