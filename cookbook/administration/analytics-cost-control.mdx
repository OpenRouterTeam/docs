## Before you start

You need:

- A management key your agent can read; the skill's scripts expect it in `OPENROUTER_API_KEY` (or passed via `--api-key`)
- Node.js with `npx` if you use the skill's scripts (they run via `npx tsx`)
- A coding agent (Claude Code, Devin, Cursor, or anything that can run shell commands)
- At least a few weeks of real usage on your account, or there's nothing to analyze

Use these references for exact schemas:

- [Query analytics endpoint](/api/api-reference/analytics/query-analytics-data)
- [Get analytics metadata](/api/api-reference/analytics/get-available-analytics-metrics-and-dimensions)
- [Management API keys](/guides/overview/auth/management-api-keys)
- [openrouter-analytics skill](https://github.com/OpenRouterTeam/skills/tree/main/skills/openrouter-analytics)

## What you're building

A cost review your agent runs for you. The conversation starts with one question:

```text lines
how can I reduce costs for next month?
```

The agent discovers the schema, pulls spend grouped by model, flags the lines where effective price per token is far above your blended rate (total spend divided by total tokens across all traffic, scaled to \$ per million tokens), drills into the API keys behind those lines, and hands you actions ranked by dollar impact.

We ran this internally and found a preview model burning ~\$6.2K/month at roughly 25x the org's blended rate. One drill-down query later, 98% of it traced to a single batch-pipeline key running a task that never needed a frontier model. The fix was a one-line model swap.

The recipes below are the building blocks of that review. Each one is a prompt you can paste into your agent, followed by an under-the-hood look at the query the agent generates and the shape of what comes back.

## Setup: install the skill and discover the schema

The skill bundles runnable query scripts so your agent doesn't hand-write `curl` calls:

```bash lines
git clone https://github.com/OpenRouterTeam/skills
cd skills/skills/openrouter-analytics/scripts && npm install
```

Schema discovery comes first. Metrics and dimensions evolve, so query what's actually there instead of trusting a doc snapshot:

```bash lines
npx tsx discover-schema.ts
```

Or hit the endpoint directly:

```bash lines
curl https://openrouter.ai/api/v1/analytics/meta \
  -H "Authorization: Bearer $OPENROUTER_API_KEY"
```

The response lists every metric, dimension, filter operator, and granularity the API currently supports; the [meta endpoint reference](https://openrouter.ai/docs/api/api-reference/analytics/get-available-analytics-metrics-and-dimensions) shows the full shape. Spend metrics (`total_usage`, `usage_*`) are in USD. Token metrics are native tokens. `cache_hit_rate` is a 0 to 1 ratio.

Two things to know before reading any output: count metrics can come back as **strings** (the reference's example shows them as numbers, so parse defensively and accept both), and `metadata.truncated` tells you whether the result hit the row limit. If it's `true`, your totals are partial; raise `limit` or narrow the query before drawing conclusions.

The API caps queries at 3 dimensions. A third dimension works only when every metric, dimension, and filter in the query is served from the activity rollups (for example `model`, `api_key_id`, `endpoint`, `workspace`, `app`, `user`, `variant`), or for the token-kind metrics below from their daily rollup (`model`, `api_key_id`, `workspace`, `variant`, `endpoint`, `provider`, `data_region`, `billed_service_tier`, `long_context`); combining three with a dimension or metric that needs raw generations (such as `country`, or latency percentiles, or `provider` without a token-kind metric) returns a 400 naming the incompatible fields. For the token-kind metrics, a third dimension also needs a `time_range` whose start and end are UTC midnights; a range of 31 days or less that starts or ends mid-day returns a 400 naming the off-midnight bound. A fourth dimension always returns a 400. When the agent needs another angle beyond that, it should run separate queries or add a time-axis `granularity` instead.

## Recipe: which models burn the most?

The widest-angle question, and the right one to start with:

```text lines
Break down my OpenRouter spend by model for last month. Compute the
effective $/Mtok for each model and flag anything far above my
blended rate.
```

Under the hood, your agent generates a query like this (one POST to `/api/v1/analytics/query` with the management key):

```json lines
{
  "metrics": ["total_usage", "request_count", "tokens_total", "cache_hit_rate"],
  "dimensions": ["model"],
  "order_by": { "field": "total_usage", "direction": "desc" },
  "time_range": { "start": "2026-05-01T00:00:00Z", "end": "2026-06-01T00:00:00Z" },
  "limit": 10
}
```

An explicit `time_range` matters: without one the API defaults to a recent window that may miss the month you asked about.

Sample response shape (1 row shown):

```json lines
{
  "data": {
    "data": [
      {
        "model": "openrouter/owl-alpha",
        "total_usage": 0.005,
        "request_count": "6",
        "tokens_total": "6331",
        "cache_hit_rate": 0.17561310238381067
      }
    ],
    "metadata": { "query_time_ms": 17, "row_count": 1, "truncated": false }
  }
}
```

From here the agent computes `total_usage / tokens_total * 1e6` for each row to get an effective \$/Mtok per model (spend over tokens gives dollars per single token; the 1e6 scales it to dollars per million tokens, the unit model pricing is quoted in). Compare each against your blended rate: the same calculation run with no dimensions, so it covers all traffic in the window. A model priced at a large multiple of the blended rate is the strongest signal to chase, but you may not find one; if every model sits near the blended rate, your spend matches your pricing and the levers are elsewhere (cache rate, prompt size, or feature surcharges, covered in the recipes below). In the internal run above, the flagged model had spent \$6,185 on 0.25B tokens (6185 / 250000000 \* 1e6 ≈ \$24.7/Mtok) with a 7.6% cache rate, about 25x that org's blended rate.

## Recipe: which keys drive a model's cost?

The model row shows where spend concentrates, but the thing you can change is the key, app, or pipeline calling that model. This works whether the model is an outlier or just your biggest fairly-priced line, since the per-key split still shows which workload to optimize:

```text lines
My spend on google/gemini-3-flash-preview looks too high. Which of
my API keys is behind it, and what is each one doing?
```

Under the hood, the agent filters to that model and groups by `api_key_id` using a `filters` array on the request body:

```json lines
{
  "metrics": ["total_usage", "tokens_total", "request_count"],
  "dimensions": ["api_key_id"],
  "filters": [
    { "field": "model", "operator": "eq", "value": "google/gemini-3-flash-preview" }
  ],
  "order_by": { "field": "total_usage", "direction": "desc" },
  "time_range": { "start": "2026-05-01T00:00:00Z", "end": "2026-06-01T00:00:00Z" },
  "limit": 10
}
```

`api_key_id`, `app`, and `workspace` resolve to human-readable names in the response, so each row names the key directly. Here's the row shape, filled with the internal run's numbers (rounded, key name changed):

```json lines
{
  "api_key_id": "batch-pipeline",
  "total_usage": 6067.0,
  "tokens_total": "127000000",
  "request_count": "37000"
}
```

The `user` dimension is the exception: grouping by `user` returns **two** fields per row instead of one. `user` is the account's display name (or `null` when the user has no name set), and `user_email` is their email (`null` when the user has no email on file). The raw user ID is never returned, so use `user_email` to cross-reference users against your own records:

```json lines
{ "user": "Ada Lovelace",  "user_email": "ada@example.com", "request_count": 42 }
{ "user": null,            "user_email": "grace@example.com", "request_count": 7 }
{ "user": "Alan Turing",   "user_email": null,               "request_count": 3 }
```

In the internal run, this is where the recommendation wrote itself: a batch-pipeline key doing 37K requests at ~\$48/Mtok is high-volume, low-complexity work on the wrong model. Repointing it to a cheap production model recovers the whole line item at near-zero risk.

A sharper variant of the same prompt skips the model step entirely:

```text lines
Are any of my keys calling preview or frontier models for high-volume
batch work? Estimate the savings from moving each one to a cheaper
production model.
```

## Recipe: what did the money actually buy?

`total_usage` is a single number. The `usage_*` components split it into what each dollar paid for:

```text lines
Break my OpenRouter spend into components: raw inference, caching,
discounts, web search, and file parsing. Are surcharges or cache
writes a meaningful slice?
```

Under the hood, the agent queries the component metrics over a time axis:

```json lines
{
  "metrics": ["usage_upstream", "usage_cache", "usage_data", "usage_web", "usage_file"],
  "granularity": "day",
  "time_range": { "start": "2026-05-01T00:00:00Z", "end": "2026-06-01T00:00:00Z" }
}
```

Each row carries a time-series key named `date__<granularity>` or `created_at__<granularity>` (here, `created_at__day`) depending on which data source the query resolves to, so accept either prefix. The rest of the row is the components in USD. Unused components come back as `null`, not 0:

- `usage_upstream`: raw inference cost
- `usage_cache`: what caching saved (or cost, for cache writes)
- `usage_data`: discounts, typically negative
- `usage_web`, `usage_file`: web search and file parsing surcharges

If `usage_web` or `usage_file` is a meaningful slice, the fix is gating those features. If `usage_cache` savings are near zero on a prompt-heavy workload, caching is your lever. And if cache rates are already high, skip the caching advice entirely; in the internal run, caching was near-maxed and the only real lever was model mix.

### Separate batch traffic

Batch API requests are recorded with the `batch` variant, so the `variant` dimension separates them from synchronous traffic at any time range:

```json lines
{
  "metrics": ["total_usage", "usage_upstream", "request_count"],
  "dimensions": ["variant"],
  "granularity": "day",
  "time_range": { "start": "2026-05-01T00:00:00Z", "end": "2026-06-01T00:00:00Z" }
}
```

Rows with `"variant": "batch"` are batch traffic. Filter with `{ "field": "variant", "operator": "eq", "value": "batch" }` to keep only batch requests, or `neq` to exclude them.

## Recipe: what did each token kind cost?

`usage_upstream` and `byok_usage` are single numbers too. The token-kind metrics break down the part of them from requests that carry the split by the kind of token it paid for, at the rates actually billed (provider discounts included), not catalog prices:

- `usage_upstream_uncached_input`, `usage_upstream_cache_read`, `usage_upstream_cache_write`, `usage_upstream_output`, `usage_upstream_reasoning`: upstream inference cost OpenRouter paid, in USD.
- `byok_usage_uncached_input`, `byok_usage_cache_read`, `byok_usage_cache_write`, `byok_usage_output`, `byok_usage_reasoning`: the same split of BYOK inference cost billed by your provider.
- `uncached_input_tokens` and `cache_write_tokens`: billed token counts for the two input kinds that have no other metric.
- `token_kind_request_count`: the requests that carry the split. Divided by `request_count`, it is the share of a row's requests the split covers.
- `usage_upstream_token_kind_covered` and `byok_usage_token_kind_covered`: the upstream cost of the requests that carry the split, the cost the parts explain, so one query returns the parts and their sum.
- `usage_upstream_token_kind_total` and `byok_usage_token_kind_total`: the upstream cost of every request in the row, split or not. Server-tool calls are left out, as they are of `request_count`.

Reasoning is its own kind only where the provider bills it at its own rate (Gemini and Perplexity today), and only on requests that carry the split: Perplexity requests whose cost Perplexity reports don't, so their reasoning cost is in neither kind. Everywhere else, including OpenAI, Anthropic, and xAI, reasoning tokens are billed and reported as output, so `usage_upstream_reasoning` is `0` while `reasoning_tokens` is not. `tokens_completion` always includes reasoning tokens, and `cached_tokens` and `reasoning_tokens` are provider-reported counts over every request, so don't divide a per-kind cost by them to get a per-token rate.

They are UTC-daily totals over any range up to a year. The same daily totals also serve `request_count`, `tokens_prompt`, `tokens_completion`, `reasoning_tokens`, `cached_tokens`, and `tokens_total`, with the same values as everywhere else, so one query can put the token counts next to the per-kind costs. The daily totals group by `model`, `api_key_id`, `workspace`, `variant`, `endpoint`, `provider`, `data_region`, `billed_service_tier`, and `long_context`, with `granularity` of `day`, `week`, `month`, or none. Any other dimension or filter (such as `app`, `user`, or `country`), `hour` or `minute` granularity, or a timezone reads raw generations instead, which allows at most 31 days; past that the query returns a 400 naming what kept it off the daily totals. A `time_range` of 31 days or less that starts or ends off a UTC midnight also reads raw generations, however far back it is, so it is not widened to whole days, and with three dimensions such a range returns a 400 instead, so use UTC midnight bounds; a longer one reads the daily totals for every whole UTC day it touches. Without a `time_range`, the default last 7 days is snapped out to whole UTC days on the daily totals, as it is on the other activity rollups.

Group them by pricing qualifiers to see where the rate came from: `billed_service_tier` (the tier you were billed at, which can differ from the tier that served the request), `long_context` (`"true"` when a long-context price tier applied), `endpoint` (the endpoint UUID, the same `endpoint_id` that [GET /api/v1/activity](/api/api-reference/analytics/get-user-activity-grouped-by-endpoint) returns with its provider), `provider` (the provider that served the request), and `data_region` (`global`, or the region the request was routed in, such as `europe`). A daily pull by model and key with one qualifier looks like this:

```json lines
{
  "metrics": ["usage_upstream_uncached_input", "usage_upstream_cache_read", "usage_upstream_cache_write", "usage_upstream_output", "usage_upstream_reasoning", "request_count", "token_kind_request_count", "usage_upstream_token_kind_covered", "usage_upstream_token_kind_total"],
  "dimensions": ["model", "api_key_id", "billed_service_tier"],
  "granularity": "day",
  "time_range": { "start": "2026-12-01T00:00:00Z", "end": "2027-01-01T00:00:00Z" }
}
```

Four things to know before summing them:

- **They start on 20 November 2026 (UTC), their first complete day.** The split is recorded as requests are billed, from the release that added these metrics; there is no backfill. On the daily totals, every metric of a row whose part of the range starts before 20 November is `null`, including `request_count`: a day row before 20 November, a week or month row when the range starts before it, and an ungranular query whose range starts before it. A week row dated 15 November reads its days from 20 November on when the range starts on 20 November. Raw generations carry the split from 18 November 2026 16:18 UTC, so a query of 31 days or less that reads them can return partial values for 18 and 19 November.
- **They sum the requests that carry the split.** Some requests don't carry it today: requests whose upstream cost the provider reports as one amount rather than per token (xAI, and Perplexity requests whose cost Perplexity reports), requests billed on fallback token estimates because the provider reported no usage, decisions requests, and batch requests. Requests whose billed rows can't be reconciled with what was charged, or whose charged amount was not recorded, don't carry it either. A row mixing them reports the parts of the requests that split. A token-kind metric is `null` only when the row holds requests of its own (non-BYOK for `usage_upstream_*` and `usage_upstream_token_kind_covered`, BYOK for `byok_usage_*` and `byok_usage_token_kind_covered`, both for the two token counts) and none of them carries the split. It is `0` when the row holds none of its requests. The two `*_token_kind_total` metrics sum every request, so they are never `null` from 20 November on. Batch requests never carry the split, so keep `variant` in the grouping (or filter it out) when a model takes both batch and synchronous traffic.
- **Check how much of a row they cover.** Request coverage is `token_kind_request_count / request_count`. Cost coverage is `usage_upstream_token_kind_covered / usage_upstream_token_kind_total` for upstream inference, and `byok_usage_token_kind_covered / byok_usage_token_kind_total` for BYOK. All four are on the daily totals, so one query returns the parts and both coverages over any range they serve. When every request in a row splits, both coverages are 1. When no request in a row carries the split (a row of xAI requests only, for example), `*_token_kind_covered` reads `null`: read its cost coverage as 0. When `*_token_kind_total` is 0, cost coverage is undefined.
- **The five kinds add up to the covered cost, up to rounding and non-token charges.** `usage_upstream` and `byok_usage` are stored to 6 decimal places and the parts to 9, so the parts of one request can differ from its cost by less than $0.000001. Charges inside an inference request that belong to no token kind stay outside the parts but inside `*_token_kind_covered`: per-image and per-second charges, Gemini cache-storage hours, tools the provider bills within the request (such as native web search), and Anthropic advisor-model tokens. Server-tool calls are separate generations; these metrics leave them out by filter, whether or not they split, as `request_count` does. Pricing qualifiers are recorded on chat, Responses, and Messages requests; other request types (embeddings, images, batch) group under an empty value.

## Recipe: is my workload prompt-heavy?

The token shape decides whether caching or prompt trimming is worth the effort:

```text lines
Is prompt caching saving me anything? Show prompt vs completion
tokens, reasoning tokens, and cache_hit_rate by model, and tell me
where caching would pay off.
```

Under the hood:

```json lines
{
  "metrics": ["tokens_prompt", "tokens_completion", "reasoning_tokens", "cache_hit_rate"],
  "dimensions": ["model"],
  "order_by": { "field": "tokens_prompt", "direction": "desc" },
  "time_range": { "start": "2026-05-01T00:00:00Z", "end": "2026-06-01T00:00:00Z" },
  "limit": 10
}
```

A 20:1 prompt-to-completion ratio points at oversized context, and a large `reasoning_tokens` share means you're paying for thinking you may not need. Pair the ratio with `cache_hit_rate`: prompt-heavy traffic with a low cache rate is the textbook caching win, while prompt-heavy traffic with a high cache rate is already optimized and the lever moves back to model mix.

## Recipe: did spend actually change?

Grouping spend over a time axis covers 2 jobs: finding what changed when a bill jumps, and verifying that a fix landed. For the first:

```text lines
My OpenRouter bill doubled this month. Find what changed, comparing
this month's spend by model and key against last month's.
```

Under the hood, the agent groups per-key spend over a weekly time axis:

```json lines
{
  "metrics": ["total_usage"],
  "dimensions": ["api_key_id"],
  "granularity": "week",
  "time_range": { "start": "2026-05-01T00:00:00Z", "end": "2026-07-01T00:00:00Z" }
}
```

Sample output:

```json lines
{
  "data": {
    "data": [
      { "date__week": "2026-06-07", "api_key_id": "batch-pipeline", "total_usage": 11.2 },
      { "date__week": "2026-05-31", "api_key_id": "batch-pipeline", "total_usage": 1402.5 }
    ],
    "metadata": { "query_time_ms": 7, "row_count": 2, "truncated": false }
  }
}
```

For the bill-doubled case, the key (or model, if the agent groups by `model` instead) whose weekly line jumped is your culprit. For verification, ask the agent to re-run the same query after a fix ships: a successful repoint shows the key's weekly `total_usage` falling off a cliff at the deploy date, like the sample above.

Filter values must match what the dimension stores internally, so agents should filter on `model` slugs (which they know exactly) and group by `api_key_id` rather than filtering on resolved key names. Save the prompts that worked and re-run them monthly; the copy-prompt at the top chains all of these recipes into one full review.

## Next steps
