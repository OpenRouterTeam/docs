# Trust-score local E2E

Stack: `packages/db/trust-score` (schema, `resolveTrustScore`, `trust_score_policies` table, KV publish), `packages/router` (advisory scoring on the transaction-attempt log), `services/cfw-internal/src/routes/trust-score` (console routes), `projects/mission-control` (`/admin-utils/trust-score`, TrustScoreCard on `/user/<clerk_user_id>`).

## Bring-up

1. Follow [local-dev-env](../local-dev-env/SKILL.md) (`bun run dev:up`), then `tilt enable internal mission-control dev-fs-logs && tilt trigger internal mission-control dev-fs-logs`. `api` (:8787) and `fake-provider` (:3002) start automatically; `internal` is :8794, Mission Control is :3001. If `db:start` fails with `migration ... is out of order ... --strict` because the shared local database already has migrations from other branches, run dbmate `up` without `--strict` against `postgresql://postgres:postgres@127.0.0.1:54322/postgres?sslmode=disable` (a sibling worktree's `@dbmate/linux-x64` binary works if the package is missing) and re-run `dev:up`. `db:reset` wipes the seeded users.
2. Do not run `bun run verify` or other heavy jobs alongside the stack. Under load cfw-internal's Postgres pool reports `exhausted database instances` and Mission Control surfaces the resulting 500 as `Could not load the trust-score policy: JSON parsing failed`. Wait for load to drop and reload before suspecting product code; a fast 401 from `curl :8794/api/v1/internal/trust-score/console/policy` shows the worker is healthy.
3. Confirm the table exists: `docker exec openrouter-web_db psql -U postgres -d postgres -c '\d trust_score_policies'`. The local database is named `postgres`, not `openrouter`. Host `psql` is absent, so always go through `docker exec`.
4. Sign in to Mission Control via [clerk-dev-signin-token](../clerk-dev-signin-token/SKILL.md). The seeded `dev+clerk_test@openrouter.ai` account may return `needs_second_factor` (MFA); generate a fresh dev account with the same script instead of bypassing MFA. If minting the ticket fails with `Unable to parse domain url` / `Failed to automatically trigger login flow`, the Infisical CLI session has expired. Log in again (`infisical login`, or `--method=universal-auth` with a machine identity and pass the printed token as `INFISICAL_TOKEN`) and retry.
5. Grant admin to the signed-in user (`bun run db:test-user` or `update users set is_admin=true where clerk_user_id='...'`). The physical column is `is_admin`; `packages/db/users/index.ts` maps it to the app-facing `is_internal_admin` that the cfw-internal admin gate checks. There is no `is_internal_admin` column, so `\d users` first if a grant errors.
6. Clerk session tokens last about 60s. If a Save shows `JSON parsing failed`, the session expired and the POST was redirected to `/sign-in`, so reload and retry.
7. Point the seeded FakeProvider endpoint at the local service. `bun run x` needs an Infisical login, which is usually absent; run the script directly instead: `set -a && . ./.env.development.local && set +a && npx tsx --tsconfig ./scripts/tsconfig.json scripts/use-local-fake-provider.ts`. It restarts `api`; wait for `GET /health 200` in `tilt logs api`.

## Publication fails silently locally

`POST /console/policy` inserts the history row and then publishes it through the Cloudflare REST API (`packages/cache/kv`), which needs `CF_KV_API_TOKEN`. Without it the KV write fails, `console.ts` wraps the failure and still returns **200**, so the editor toasts `Saved trust-score policy vN`, the banner reads `Latest saved version vN.`, and the editor origin moves to the new row even though KV was never written. Treat none of those as proof of KV publication. `tilt logs internal` shows the `trust-score-policy-publish-failed` error line with `Missing CF_KV_API_TOKEN environment variable`, followed by the `GET …/policy` and `GET …/policy/versions` refetches. Check `services/cfw-internal/src/routes/trust-score/console.ts` for the current DB/KV ordering before asserting it.

To exercise the failed-save path (`[data-testid=trust-score-policy-error]`, edited values kept, history refetched without a reload) return a 5xx from the route, for example by stopping Postgres or throttling the request in devtools; the KV failure alone no longer produces it. `useSaveTrustScorePolicy` invalidates the `policy` and `versions` queries on both success and failure, so expect a `GET …/policy` and `GET …/policy/versions?limit=100` right after the POST in `agent-browser network requests`. If the list still says "No policy versions saved yet" until reload, Mission Control is running stale code.

Capture the unscored-published Preview **before the first save**, while `trust_score_policies` is empty. Expect `Unscored` plus `No published trust-score policy is currently available.` (no reasons table, no "No terms matched" sentence) while the draft column is scored. `POST /console/evaluate` scores the published column from the newest Postgres row (`evaluate-user.ts`), not from KV, so after any save the Published column scores against that row. The preview is a submitted snapshot, not a live publication-status indicator. For a separate router inference test, seed its local live-config key:

```sh
docker exec openrouter-web_db psql -U postgres -d postgres -Atc \
  "select jsonb_set(document, '{version}', to_jsonb(version)) from trust_score_policies order by version desc limit 1" > /tmp/policy.json
cd services/cfw-api && npx wrangler kv key put --local --persist-to ../../.wrangler/shared-state \
  --namespace-id d585bc8446184f5488b55d038337e839 trust_score_policy --path /tmp/policy.json
```

Postgres stores `version` in its own column, so the raw `document` has no `version` field and the router's schema rejects it; the `jsonb_set` above injects it. The namespace id is the `live-config` KV binding in `services/cfw-api/wrangler.toml` (`KVNamespace.LiveConfig`); check it if the put is silently ignored. Local KV seeding does not change what the console reads from Postgres.

## Gotchas

- The TrustScoreCard exposure block needs `usage-record` running next to `internal` and `mission-control`. A direct `wrangler dev` of usage-record inherits the production `[vars]` and the worker reports Ready while every call fails with `oidcMiddleware.decodeJwt` / `Invalid JWT`. Start it through `services/usage-record/scripts/dev.ts` (the package `dev` script) or pass explicit `--var OR_ENV:development --var SPANNER_PROJECT_ID:openrouter-dev --var SPANNER_INSTANCE_ID:dev --var SPANNER_DATABASE_ID:usage --var SPANNER_EMULATOR_HOST:localhost:9010`.
- The usage windows behind the evaluate response (and the burn-rate ceiling) are overlaid from usage-record/Spanner, not read from `analytics_users`. Seed current-period `budget_usage` rows for the never/daily/weekly/monthly windows. Emulator REST timestamps need an uppercase `Z` suffix and both `created_at` and `updated_at`.
- Console-evaluate requests never create `services/dev-fs-logs/.logs/gen-*` directories, so their evidence is the browser response (`agent-browser network request <id> --json`) plus the cfw-internal request log, not a generation log.
- Restarting `internal` or `usage-record` outside Tilt can leave the old workerd children alive on the inspector ports (`9229`, `9321`), so the new worker fails to bind. Check `ss -ltnp` for both the HTTP and inspector listeners and stop the whole old process tree before starting again.
- An empty `trust_score_policies` table renders the card as `Unscored` while the exposure block still works. Check the table has the intended fixture before treating a missing score as a regression, and reseed it through SQL rather than the repository seed files.
- Mission Control scrolls inside a fixed-height container, so a `--full` screenshot stays viewport-sized. Capture the card at the normal viewport for UI assertions and, for whole-page evidence, temporarily raise the viewport height past the nested `scrollHeight`.
- The first inference after an `api` restart logs `trust_score: null`. Live-config reads never block, so a cold isolate serves the schema default and refreshes in the background. Send a second request before concluding scoring is broken.
- The TrustScoreCard and `POST /console/evaluate` score the published policy read from Postgres (`policy_source: published | draft | none`), while inference reads KV. A scored console result is not proof that the KV write succeeded. Only the preview's "Unsaved draft" column uses `policy_source: draft` (prospective version = latest + 1).
- Preview depends on the usage-record RPC. Right after a full-stack start both evaluation POSTs can fail with 500 (`JSON parsing failed` in the UI, proxy socket resets in the Next log) while the policy and history GETs work. Confirm usage-record is Ready in Tilt, then cycle only internal (`tilt disable internal && tilt enable internal`) and retry. Keep the initial failed statuses in the report rather than attributing every JSON error to an expired Clerk session.
- Family caps apply to the draft preview. With an Identity max credit of 20, raising `personal_account` to +20 yields 70 (applied +16/+4), not 75. Raise the cap (or pick a term outside the cap) before expecting the naive sum.
- `/user/<id>` has two `Refresh` buttons (Entitlements and the trust-score card); target `[data-testid=trust-score-card] button` to check the evaluate re-POST.
- Term-dialog fields: `#trust-score-term-id`, `#trust-score-term-label`, `#trust-score-term-points`, `#trust-score-term-half-life`, `#trust-score-term-max-score` (only after selecting the Ceiling radio); row actions are `button[aria-label='Edit <label>']` / `Remove <label>`; rows are `[data-testid=trust-score-term-<id>]`; preview input is `#trust-score-preview-user`; notes is `#trust-score-notes`. Expected messages: `terms: duplicate term ids: <id>`, `Enter a label.`, `Points are at most 100.`, `The half-life must be a positive duration.`, `The ceiling is at most 100.` / `The ceiling is at least 0.`. With zero conditions the dialog reports only `Add at least one condition so the term can match.`, so add a condition before checking the other messages.
- `POST /console/evaluate` returns `data.{resolution, policy_source, user_fields, risk_flags}`. With no published policy and no draft, `resolution` is `null` and `policy_source` is `none`; a 500 here means stale cfw-internal code. The `draft` body must not carry `version` (400 `Unrecognized key: "version"`), so strip it with `jq 'del(.version)'` when replaying `data.latest.policy` from `GET /console/policy`.
- A new term starts with no conditions and its field picker offers only user and risk-flag fields; for a term that matches the signed-in dev user without payment or IP data, pick the `Account email` field with the `domain is` operator and the user's email domain (`openrouter.ai` for a `devin+clerk_test_*@openrouter.ai` account). With base score 50 and one `+10` behavior term the draft column shows `60 / 100`.
- Preview snapshots the draft at submit time. To check it, note the browser's `POST /api/trust-score/evaluate` count before editing: base-score and term edits leave the count and the rendered score unchanged until Preview, each valid Preview (including a repeat with no edits) sends one evaluation carrying `draft` and `compare_published: true`, and an invalid submitted draft sends only `{clerk_user_id}` for the published column. Clear controlled inputs with native Ctrl+A and Backspace, since an automation `fill ''` can blank the field without updating React state. The editor's inline validation alert appears only after an attempted save, so the Preview warning is the signal that the submitted draft is invalid.
- The console evaluate route scores the account with no request, so a draft term with a `request_dim` condition (only reachable by loading a version saved before the picker was scoped to user fields) is evaluated against an empty request and can score differently at inference (a `missing` request filter or an OR branch without request conditions can still match). The draft column carries a warning alert (`[data-testid=trust-score-preview-request-dimension-terms]`) naming those terms; the published column never shows it.
- With a valid draft both columns and the delta line (`[data-testid=trust-score-preview-delta]`) come from one `POST /console/evaluate` response: `resolution` scores the draft and `published_resolution` scores the published policy against the same evidence and `now`, so the delta is a pure policy difference (both `evaluated_at` values match). A `null` `published_resolution` renders the published column as `Unscored`, a missing one renders a warning that the column is unknown. Do not expect a second, draft-less evaluate request while the draft is valid.
- Version history requests `/api/trust-score/policy/versions?limit=100` (the constant lives in `PolicyVersionHistory.tsx`). With no saved versions the card reads `No policy versions saved yet.` and `Load into editor` cannot be exercised without a save.
- `Load into editor` restores the base score, family caps, and terms of the chosen version, clears the Notes textarea and the save alert, and keeps the latest version as the save target so the next `Save and publish` still sends the latest `base_version`. The toast reads `Loaded v<n> into the editor` / `Nothing changes until you save and publish.` in the `Notifications` region and auto-dismisses, so take the screenshot right after the click.
- The editor card description carries `[data-testid=trust-score-editor-origin]` reading `Editing v<n> unchanged.` while the form still equals a saved version, and the matching history row shows a disabled `In editor` button instead of `Load into editor`. On page load it names the latest version. Any base-score, cap, or term edit removes the caption and re-enables the row; a successful save points it at the new version. Notes edits do not clear it because notes are not part of the versioned policy.
- Every `Load into editor` button is disabled while `Save and publish` is in flight, so a historical load cannot replace the form under a pending save. The local save settles quickly, so this state is easiest to see with devtools network throttling.
- A local 502 on `Save and publish` inserts the history row but does not move the editor origin: an edited draft stays originless and an unchanged loaded version keeps its caption and its disabled `In editor` row. Do not expect the newly inserted row to become the editor origin.
- A save that fails with a 5xx (the row may still have been inserted) does not move the editor origin: an edited draft stays originless and an unchanged loaded version keeps its caption and its disabled `In editor` row. Do not expect the newly inserted row to become the editor origin.
- On first load the Mission Control global search combobox may be expanded and swallow `agent-browser click "text=..."` selectors (`Element not found`). Press `Escape`, then drive the page through `agent-browser snapshot -i` refs instead of text selectors.
- `/user/<unknown id>` short-circuits with a page-level `Error: User not found`, so the card's own error state is not reachable there. Use the Preview panel with an unknown id (both columns show `User not found`) or curl `POST /console/evaluate` (404).
- Direct curl against `:8794` needs the full browser cookie header (`document.cookie` from the Mission Control tab, including `__client_uat`, or `agent-browser cookies get` minus the `generaltranslation.*` entries joined with `;`) plus `Origin: http://localhost:3001`. A non-admin cookie gives a concealed 404 on every route. On every console route a bare `__session=<jwt>` cookie or no cookie gives a generic `Unauthorized` 401. A verified Devin OIDC bearer is admitted on every console route.
- Evidence for a generation lives in `services/dev-fs-logs/.logs/gen-<id>/router/transaction-attempt.log` (`trust_score`, `trust_score_policy_version`, `trust_score_reasons` as a comma-joined string of term ids). No `gen-*` dirs exist until the first request. The dev-fs-logs viewer (:3011) virtualizes the code view, so `trust_score*` lines only enter the DOM after scrolling the `overflow-auto` container to the bottom; `grep` the file on disk instead.
- Request a fake-provider completion with `{"model":"openai/gpt-4.1-2025-04-14","provider":{"order":["fake-provider"],"allow_fallbacks":false}}`, header `X-Completion-Tokens: 5`, key `sk-or-v1-unlimitedkey` (owner `user_2xyeKet6gI2xZ0U4UoshenrrGi1`, the seeded dev user).
- Mission Control shows a pre-existing Next dev "1 Issue" hydration warning from `components/NavBar.tsx` on every page; it is unrelated to trust score.

## Cleanup

If a Save-and-publish attempt inserted a new version, `delete from trust_score_policies where version=<n>` to restore the seeded history. Revert admin grants you added (`update users set is_admin=false where clerk_user_id in (...)`) and, if you seeded KV, `wrangler kv key delete --local --persist-to ../../.wrangler/shared-state --namespace-id d585bc8446184f5488b55d038337e839 trust_score_policy`.

- `CF_KV_API_TOKEN` (Cloudflare KV API token for the live-config namespace), only if the KV write behind Save and publish must succeed locally; otherwise use the seed fallback.
