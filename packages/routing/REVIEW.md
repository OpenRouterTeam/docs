# Review Guidelines

## Policy composition

* When two restriction sources apply to the same routing decision (for example request-level `provider.only` and the account-wide Allowed Providers list), they must be intersected, never substituted. Selecting one source when the other is present silently widens the effective policy; an empty intersection must fail the request rather than fall back to either source alone. This was fixed for allowed providers in [PR #33629](https://github.com/OpenRouterTeam/openrouter-web/pull/33629) (`packages/routing/filters/by-allowed-providers.ts` and `packages/router/plugins/base/policy-eligible-models.ts`); flag any new filter that merges independent restriction inputs with anything other than intersection semantics.

## Critical Areas
* The LLM & Embeddings Routers have parallel lists of filter steps. When steps are added/removed/modified in one but not the other, verify that it is expected, and ensure the differences are intuitively documented.
  * `reorderEndpointsByMinThroughput` and `reorderEndpointsByMaxLatency` are intentionally absent from the embeddings pipeline. `preferred_min_throughput` and `preferred_max_latency` are chat-completion latency / throughput preferences; embeddings endpoints do not expose comparable per-request throughput heuristics, so these reorders would have no signal to act on. Revisit when embeddings gain analogous runtime metrics.
  * `filterByEncryptedPayloadEndpoint` is intentionally absent from the embeddings pipeline. It pins routing to the endpoint named in encrypted-payload routing traits carried by `reasoning_details` and Responses passthrough items; embeddings requests carry no messages, reasoning details, or passthrough items, so they can never carry encrypted payload traits.
  * `filterEndpointsByRestrictedNativeToolSupport` is intentionally absent from the embeddings pipeline. It gates on restricted native tool types (e.g. the Anthropic advisor tool `advisor_20260301`) that only chat-completion requests carry; embeddings requests cannot carry tools at all.
  * `filterEndpointsByMidConversationToolChangesSupport` is intentionally absent from the embeddings pipeline. It gates on Anthropic deferred custom tools and mid-conversation tool-change constructs (`tool_addition`/`tool_removal` blocks) that only chat-completion requests carry; embeddings requests cannot carry messages or tools at all.
  * `filterByEndpointId` is intentionally absent from the embeddings pipeline. It reads `context.user.internalPinnedEndpointId`, which is only ever populated by `applyInternalEndpointPin` on routes that call it (the chat routes, plus the image / video / TTS / STT / rerank routes); the embeddings route never applies the pin, so the step would always skip there. Add it alongside `applyInternalEndpointPin` if embeddings ever gains pin support.
  * `filterEndpointsByStreamFunctionCallArgs` is intentionally absent from the embeddings pipeline. It prefers Vertex Gemini endpoints when `stream_function_call_arguments` is requested (a Gemini function-calling streaming flag); embeddings requests cannot carry tools or function calls at all. TODO(stream-fc-args stopgap): remove this filter once Google AI Studio supports streamed function-call arguments.
  * `filterBatchOnlyEndpoints` runs first, then `filterByEndpointId` yields `Mutate` (like `filterByEncryptedPayloadEndpoint`), never `EarlyReturn`: the candidate set narrows to the pinned endpoint but every later hard gate (data region, credits, guardrails, data policy, disabled status, ...) still evaluates it, and a gate rejection fails the request outright with no fallback. An `EarlyReturn` would bypass every later step and let a pinned request to a hidden/draft endpoint skip the compliance gates. A deliberate consequence: `filterByEncryptedPayloadEndpoint` runs on the narrowed set, so a pinned request replaying encrypted reasoning/compaction payloads produced by a *different* endpoint fails with the encrypted-payload 404 instead of the endpoint pin silently winning — the pinned endpoint could not decrypt those payloads anyway, so the request would only have failed later at the provider.
  * `filterRealtimeOnlyEndpoints` runs right after `filterBatchOnlyEndpoints` in the text-completion pipeline and is intentionally absent from the embeddings pipeline. It drops endpoints with `features.supports_realtime === true`, which are served only by `cfw-realtime-api` over WebSocket, and 404s with a pointer to the Realtime API when nothing else remains. Realtime endpoints are speech-to-speech chat models (OpenAI and Google AI Studio), so only the chat pipeline can be handed one; no embeddings model carries the flag.
  * `filterEndpointsByBatchSupport` (defined in `packages/embeddings/routing/filter-by-batch-support.ts`) is intentionally absent from the text-completion pipeline. It drops Vertex prompt-prefix embedding endpoints (e.g. `gemini-embedding-2`) that cannot serve batch (multi-input) requests; chat-completions requests have no multi-input batch shape.
  * `filterNonByokBlocklistedEndpoints` is intentionally absent from the embeddings pipeline. The blocklisted endpoint IDs target chat-completion providers for `anthropic/claude-5-fable-20260609`; those providers do not serve embedding models.
  * `filterOrgExcludedEndpoints` is intentionally absent from the embeddings pipeline. The per-org excluded endpoint IDs target a chat-completion Fireworks kimi-k3 endpoint that does not serve embedding models.
  * `applyFortunaRouting` is intentionally absent from the embeddings pipeline. Fortuna scoring is designed for chat-completion provider selection where multiple providers offer the same model with different margin/latency/reliability tradeoffs; embeddings endpoints do not have comparable provider diversity or scoring heuristics.
  * `filterEndpointsByRegionalSurcharge` is included in the embeddings pipeline. The filter targets Anthropic, OpenAI, and Google models on endpoints that carry a regional surcharge: non-US regions (Bedrock EU, Vertex EU, Azure swedencentral), Bedrock endpoints in a US region (both `us.*` geographic cross-region profiles and unprefixed in-region foundation IDs like Mantle's `openai.gpt-5.6-sol`, which bill the pricier in-region tier), and Vertex endpoints in a US location (the `us` multi-region and individual data centers like `us-east5`; only Vertex `global` is standard price) serving either an Anthropic model or a GA Gemini 3+ model. The Google case is narrower than the other two authors: only Vertex endpoints whose `provider_model_id` is a GA (non-preview, non-`-exp`) Gemini model of major version 3 or above bill Google's non-global premium, so Gemini 2.5 and non-versioned IDs stay in default routing. That exemption is what keeps `gemini-embedding-2` unaffected in the embeddings pipeline — a future versioned Gemini 3+ embedding model on a non-global Vertex region would be dropped. OpenAI offers embedding models through Azure, which could serve them on regional endpoints with surcharges. The filter exempts a surcharge endpoint for BYOK users only when a prioritized (or, for `is_byok_only` endpoints, any) matching BYOK key would produce a customer-billed copy AND the same provider has no standard-priced endpoint for the model variant among the candidates; when it does, BYOK users default to the standard endpoint exactly like non-BYOK users. Its companion step `dropSurchargeEndpointsAfterBYOK` runs in `orderingTailRoutingSteps` (and the chat and video pipelines) directly after `addBYOKEndpoints`: it removes the platform-billed originals the exemption let through so the surcharge is never billed through OpenRouter credits. Any pipeline that includes both the surcharge filter and `addBYOKEndpoints` must also include the companion step. HIPAA-refused workspaces get no BYOK exemption at all: the post-BYOK HIPAA pass removes every BYOK copy, and the companion step's empty-pool guard (needed so an all-surcharge pool a non-BYOK request kept pre-BYOK still routes) would otherwise hand the platform-billed original back.
  * `filterEndpointsByDataPolicy` and `filterEndpointsByGuardrail` filter each platform endpoint by the data policy `withExpectedByokCopyDataPolicy` gives it: a prompt-retaining original survives when `addBYOKEndpoints` will make a declared-ZDR BYOK copy from it. Any pipeline that runs either pre-BYOK step together with `addBYOKEndpoints` must also run the matching post-BYOK step (`dropDataPolicyRetainingEndpointsAfterBYOK`, `dropGuardrailRetainingEndpointsAfterBYOK`) after it. The post-BYOK step filters the whole pool by each endpoint's own data policy and removes the original and any undeclared retaining copy. Without it the retaining original stays routable under a ZDR constraint. Video is the one exception: `canHonorDeclaredZdr` is false for every video endpoint, so the pre-BYOK step never keeps an original through and the video pipeline takes no post-BYOK half. Private endpoints (`is_private`) are outside the declaration entirely: the row carries an ops-verified per-deployment policy, so `withExpectedByokCopyDataPolicy` is identity for them and `applyDeclaredDataPolicy` leaves their copies unstamped in both directions.
  * `filterEndpointsByDataRegion` judges each platform endpoint through `projectDeclaredRegionByokCopy`: an out-of-region original survives when `addBYOKEndpoints` will make a BYOK copy of it from a key whose `declared_region` is the request's region. Any list that runs `filterEndpointsByDataRegion` with a `context` together with `addBYOKEndpoints` must also run `dropOutOfRegionEndpointsAfterBYOK` after it. The post-BYOK step filters the whole pool through `isByokCopyInDataRegion` (the endpoint's own `provider_region`, or for a BYOK copy the region declared on the key behind `byok_provider_key_id`) and removes the kept-through original and any copy from an undeclared or otherwise-declared key. Without it the out-of-region original stays routable on a regional hostname. Video is the one exception, exactly as for ZDR: `canHonorDeclaredRegion` is false for every video endpoint, so the pre-BYOK step never keeps a video original through and the video pipeline takes no post-BYOK half. Never write `provider_region` on a BYOK copy to express the declaration — adapters read it to pick upstream URLs. Outside the declaration, so the row's own region answer stands in both directions: private endpoints (`is_private`), cross-region inference profiles (`global.*` model ids), video output models, and rows whose own `provider_region` is any non-empty value other than the literal `global` that is not already inside the declared region (a pinned region on the other side, a third region such as `asia-southeast1` or `SG`, or an unclassifiable string — our adapter dispatches to that pinned location regardless of the customer's account); `canHonorDeclaredRegion(endpoint, declaredRegion)` is false for all four. Only a null, empty, or literal `global` `provider_region` pins nothing and stays honorable, and an already in-region value is harmless. The guardrail `allowed_data_regions` restriction is a separate org policy still judged on raw `provider_region`: the pre-BYOK `filterEndpointsByGuardrail` skips that check, so `dropGuardrailRetainingEndpointsAfterBYOK` runs it and must therefore run for a region declaration as well as a ZDR one, dropping the declared copy under the restriction whether or not the key also declares ZDR (intentionally fail-closed; see the header of `endpoints/is-byok-copy-in-data-region.ts`). The step skips under a Global request and when no request key `hasRegionDeclaration`, so undeclared and Global-declared keys change no routing outcome.
  * `prioritizeServiceTierEndpoints` is intentionally absent from the embeddings pipeline. Service tiers only exist for LLM inference; embeddings endpoints have no flex/priority tier rows to prioritize.
  * `filterEndpointsByTierEndpointRows` is intentionally absent from the embeddings pipeline (and the other modality pipelines). It excludes real tier endpoint rows (persisted `service_tier` column) from default routing; tier rows are only created for LLM inference endpoints, so no such rows can appear in those pools. If tier rows are ever created for another modality, that pipeline must gain this step first.
  * `filterEndpointsByFlexServiceTier` is intentionally absent from the embeddings pipeline. It restricts `service_tier: "flex"` requests to flex-tier endpoint rows; embeddings endpoints have no flex/priority tiers (see the `prioritizeServiceTierEndpoints` rationale above).
  * `filterByEndpointId` yields `Mutate`, so later steps still run on a pinned request. Endpoint-ID pinning is internal-only (`INTERNAL_ENTITY_IDS`) and implies "use this exact endpoint". `addBYOKEndpoints` still runs: if the internal entity has a matching BYOK provider key, a BYOK copy of the pinned endpoint is appended and later reordering can select it — acceptable because both copies hit the same provider deployment. A pinned `is_byok_only` endpoint with no matching key is dropped there, yielding a generic no-endpoints error; that gate is a hard requirement, not a fallback opportunity. Likewise, a pinned request with `service_tier: "flex"` whose pinned endpoint is not a flex row 404s: `filterEndpointsByFlexServiceTier` removes the pinned endpoint, leaving no candidates. Failing outright rather than silently serving the default tier is the intended consequence of the pin honoring all later gates — internal callers pinning a specific endpoint should not request tiers that endpoint does not offer.
* `filterEndpointsByRegionalSurcharge` inclusion criteria: when adding this filter to a new modality pipeline, verify the modality actually has providers on regional endpoints. The filter is included in embeddings because OpenAI offers embedding models through Azure regional endpoints, but excluded from rerank because no rerank provider uses regional endpoints yet.

* Private endpoint priority is included in all modality routing pipelines (text, image, embeddings, STT, TTS, video, rerank). The step safely no-ops when the caller does not pass grant fields.

## Private endpoints and data policy

* A private endpoint row (`is_private`) is filtered by its own effective `data_policy` — endpoint override, else provider policy, with video output forced to retain (`endpoints/constructor.ts` `getRetainsPromptsForEndpoint`). No ZDR predicate (`isZdrEndpoint`, `getFailingDataPolicies`, `checkZdrViolation`) reads `is_private`; flag any filter that special-cases private rows when evaluating the effective data policy. The one intended special case is the per-key ZDR declaration: `applyDeclaredDataPolicy` returns a private row's BYOK copy unstamped and `withExpectedByokCopyDataPolicy` skips private rows, so the row's policy wins over `declared_zdr` in both directions (a `true` key cannot widen a retaining private row, a `false` key cannot narrow a ZDR one). `private-endpoint-zdr.test.ts` pins both through `routingSteps`.
* Private rows are region-classified by `provider_region` exactly like public rows: `filterEndpointsByDataRegion` runs on the merged pool, `isProviderRegionInDataRegion` treats null / `''` / `global` and a `global.*` inference profile as out of region, and a BYOK copy inherits `provider_region` through `makeBYOKEndpoint`. A grant (`prioritizePrivateEndpoints`) and the internal pin (`filterByEndpointId`) only order or narrow; neither admits a row the region step would drop. Flag any step that lets a granted or pinned row bypass admission. Routing trusts `provider_region` as written: nothing here checks it against the row's `provider_overrides.baseUrl` or the BYOK key's own endpoint, so whoever writes a private row (Mission Control, or `buildEndpoint` in `services/cfw-frontend-api/src/routes/private-deployments/management-handler.ts`, which inherits the blueprint's `provider_region`) owns its truthfulness. `private-endpoint-data-region.test.ts` pins the routing half.
* Model-level eligibility sets (`getZdrPermaslugs`, `getHipaaPermaslugs`, `getRealtimePermaslugs`, `getRegionPermaslugs` in `models/filter-helpers.ts`) exclude private rows via `isPublicEndpoint`, regardless of the cache they receive, because a private endpoint must not make its model look eligible to entities without a grant. Flag a new eligibility set that iterates an endpoints cache without the `!is_private` guard, and flag any caller that builds such a set from an `EndpointVisibility.All` cache.
* Never scope those sets or their callers per entity. `services/cfw-frontend-api/src/routes/catalog/models-find/route.ts` is an unauthenticated, CDN-cached public route (`public, max-age=60, s-maxage=60, stale-while-revalidate=300`); a per-entity result there is a cache-poisoning hazard. Per-entity private catalogs go through `buildPrivateRoutingCaches` + `mergePrivateCatalog` (`private-routing-caches.ts`, used by `list-user-models`).
