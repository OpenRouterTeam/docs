# Guardrail reference cleanup

Acquire the complete reference barrier set at transaction entry, before account or child row locks. `lockGuardrailMutationsInTransaction` takes owning `accountIds` and every `referenceUserIds` value the transaction may introduce (actors and member subjects). It acquires shared per-user barriers for both sets, then exclusive per-account locks. Account deletion and DSR take exclusive barriers for every deleted subject before discovering and locking the accounts that reference them, so discovery includes every earlier writer and remains stable through cleanup. Keep the discovery predicates in `delete-for-users.ts` aligned with the cleanup writes.

Lock order is reference barriers, account locks, then row locks; collect complete sets before acquiring any lock, sort IDs within each set, and never upgrade a writer transaction into cleanup. Revalidate owners, actors and subjects after waiting. Existing writer entrypoints use `prepareGuardrailWriteInTransaction`; missing/deleted owners and actors and known deleted members are rejected. Historical members without local user rows remain valid only through their exact membership FK. Migration and management writers must re-read retained sources under the barriers; a deleted source cannot be initialized again. Keep transactions bounded and exclude network work. These locks never run on inference paths.
