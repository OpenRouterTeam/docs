# Workspace capabilities: restricted workspace modes

How OpenRouter removes product surfaces from restricted workspaces (today: HIPAA, via the one-way `workspaces.is_hipaa_enabled` flag). This is the reference for the whole system: the policy table, the UI gates, the route and endpoint manifests, and the governance that keeps future features from bypassing it.

## The model in one paragraph

A **workspace mode** (`WorkspaceMode`: standard, hipaa) is *subtractive*: it removes **capabilities** (`WorkspaceCapability`: chatroom, fusion, ...) from a workspace. This is deliberately a different axis from entitlement gates (`gates/*.ts`), which *grant* features additively — `hipaaGate` decides who may turn HIPAA on for a workspace; the capability table decides what an enabled workspace loses. A capability names a product surface gated as a unit, never an individual UI element: leaf controls (buttons, toggles, CTAs) inherit the capability of the surface they serve. A surface can also be a data-egress behaviour — adding a broadcast destination, adding a BYOK key — whose add-control is gated in-surface while the page listing existing items stays available in every mode, so a restricted workspace can still remove what it already has (see Enforcement status → Leaf-affordance capabilities).

The single policy point is `workspace-capabilities.ts`. Standard mode is the unrestricted base (an exhaustive switch, everything true); each restricted mode is an **additive allowlist** over that base — an explicit granted set, empty for HIPAA — so a new capability is denied in restricted modes with no edit at all, and *granting* is the only possible change. The table test's completeness check still forces an expected-availability row for every (mode × capability) pairing, so every pairing remains a recorded decision.

## The invariant

**No page route renders and no frontend-api endpoint serves without a declared classification.** A classification is either the `WorkspaceCapability` that governs the surface or the explicit `AVAILABLE_IN_ALL_MODES` opt-out — silence is never a pass. Two completeness tests enforce this in CI, and the classification files are code-owned, so every new surface gets a human decision (see Governance).

## How to

**Gate an existing surface for restricted workspaces**: change its row in the capability table (or its manifest classification) — one line. Everything downstream reads the table.

**Add a new capability**: add the enum entry; restricted modes deny it automatically (empty-by-default granted sets), and the table test forces the expected-availability rows so the denial is still a recorded decision. Then classify the surfaces it governs in the route manifest and endpoint registry, and gate in-surface affordances with `useWorkspaceCapabilityGate`. For an endpoint mount, pick the kind by what the routes act on: mount `requireWorkspaceCapability(<capability>)` on a route app whose routes act on the caller's active workspace, or — when the routes name their workspace in the body or query — classify the mount `gatedPerRoute(<capability>)` and gate the specific add/exercise routes with `assertWorkspaceCapability` / `assertWorkspaceCapabilityById` (next section). For a leaf-affordance capability (the add-control of a page that must stay reachable), leave the page `AVAILABLE_IN_ALL_MODES`, gate the control on the viewed workspace row with `useWorkspaceCapabilityForWorkspace`, show the standard `CAPABILITY_UNAVAILABLE_IN_WORKSPACE_COPY` treatment, gate the add/exercise routes per the previous sentence, and record in Enforcement status where the server also refuses the data movement itself.

**Blocked responses carry one error code.** Every capability-blocked 403 that `cfw-frontend-api` or `cfw-public-api` produces — from the endpoint middleware or from a per-route gate — sets `error.metadata.code` to `WORKSPACE_CAPABILITY_UNAVAILABLE_ERROR_CODE` (`workspace_capability_unavailable`) and `error.metadata.capability` to the capability refused. Clients branch on that code, never on message text, so a new gate must build its refusal from the shared helper rather than inventing a code of its own; a gate may override the message (the existing prompt-storage and data-discount gates keep their surface-specific text) but never the code. The capability checks that do not carry the code are listed under Enforcement status → Capability checks without the code.

**Add a new page route**: the completeness test fails until you classify it in `workspace-route-capabilities.ts`. Choosing `AVAILABLE_IN_ALL_MODES` is a reviewed decision — say in the PR why the surface is safe for restricted workspaces.

**Add a new frontend-api endpoint**: same, in `workspace-endpoint-capabilities.ts`. Capability-classified prefixes must also mount the middleware; prefixes whose routes name their workspace use `gatedPerRoute(...)` and the target-workspace gate instead (next section).

### Target-workspace gates

`requireWorkspaceCapability` resolves the caller's **active** workspace from the `or_active_workspace` cookie. Many frontend-api endpoints do not act on that workspace: they take a `workspaceId` in the JSON body or a `workspace_id` in the query and act on the workspace they name. A direct API call can keep a standard workspace active while naming a restricted workspace's id, so for those endpoints the middleware is not the boundary — the row of the workspace the request names is. `packages/entitlements/workspace-capability-gate.ts` (importable as `@openrouter-monorepo/entitlements/workspace-capability-gate`) is that check: `assertWorkspaceCapability({ workspace, capability, location })` for handlers that already hold the row, and `assertWorkspaceCapabilityById({ workspaceId, entityId, capability, location })` for handlers that do not (it loads the row within the caller's entity, answers 404 when it is not theirs, and returns the row so the handler can reuse it). Both refuse with `WORKSPACE_CAPABILITY_FORBIDDEN_MESSAGE` (or the optional `message` override) and the shared `metadata.code`; the middleware builds its refusal from the same helper.

Such a mount is classified `gatedPerRoute(<capability>, ...)` in `workspace-endpoint-capabilities.ts` — a third classification kind beside a capability and `AVAILABLE_IN_ALL_MODES`. It records that the route module, not the middleware, gates the named routes, and the completeness test's per-route linkage check requires the route module's directory to reference every listed `WorkspaceCapability.<Member>`. The entry's comment must say precisely which routes are gated and why the rest stay open.

**Reads stay open; removals and disables stay open.** A per-route gate covers only the writes that add or exercise the surface (create, update, enable, upload, run). Lists, downloads, deletes and `enabled: false` writes pass in every mode, so a restricted workspace can always see and remove what it already holds — the "enabling is gated, disabling is always allowed" precedent set by the prompt-storage and data-discount gates. For a standard workspace a per-route gate is a no-op; the only added cost is at most one `getWorkspaceById` read on a gated write where the handler did not already hold the row.

**Add a new mode** (e.g. a future compliance tier): add the `WorkspaceMode` entry, give it its own (empty) granted set in the mode switch, and add its rows to the table test's expected-availability grid; it denies everything until capabilities are explicitly granted.

## Posture decisions (and why)

- **UI gates are UX; the endpoint middleware is the intended boundary.** Client gates fail *open* on a member-fetch outage (matching the ENT-1686 no-workspace gate: failing closed would brick surfaces for everyone during an outage). The middleware fails *closed* on every error path — org-only token, zero workspaces, member-fetch error. See Enforcement status for what is actually wired today.
- **Default-closed everywhere it matters.** Restricted modes are additive allowlists (empty granted sets, so omission denies); unclassified routes are blocked at runtime in restricted workspaces even though CI should make them impossible; unreachable switch branches return false.
- **One disabled treatment.** Nav and menu entries for blocked surfaces stay visible but disabled — the top nav and menus through the shared `CapabilityDisabledNavItem` components, the dashboard sidebar through `NavItem.disabledReason` — all quoting the standard "Not available in this workspace" reason (`CAPABILITY_UNAVAILABLE_IN_WORKSPACE_COPY`), so users understand the restriction instead of the surface silently not existing. Blocked routes render the shared panel. Do not invent per-surface variants.
- **Optimistic while loading.** Nav links and dashboard routes render during workspace resolution so the unrestricted majority never sees layout shift; the route guards and the boundary catch early clicks. Chat/fusion own their loading presentation in-surface.
- **The active workspace is resolved one way.** Cookie + membership via `listMemberWorkspaces` + `pickActiveWorkspace` — the same order as the workspace switcher and cookie-auth inference. Do not re-derive it.
- **Two workspaces can be in play: the cookie workspace and the URL workspace.** The *cookie workspace* is the one the active-workspace cookie names — the switcher writes it and cookie-auth inference reads it. The *URL workspace* is the one `[workspaceId]` names in a `/workspaces/[workspaceId]/…` path, which `[workspaceId]/layout.tsx` resolves server-side (membership, slug canonicalisation, org-admin visibility). The cookie does not follow navigation, so a user can view `/workspaces/<other>/files` while a different workspace is the cookie workspace. Routes under `/workspaces/[workspaceId]` render the URL workspace's data, so they are judged by it: judging them by the cookie workspace would block a standard workspace's page because the cookie workspace is HIPAA, or allow a HIPAA workspace's page because the cookie workspace is standard. `UrlWorkspaceRouteCapabilityGuard` reads the already-resolved row synchronously, and `CookieWorkspaceRouteCapabilityGuard` defers those manifest entries (`isRouteJudgedByUrlWorkspace`) without fetching the member list. The rule is really "judge a surface by the workspace whose data it acts on": the nested Chat and Fusion shells under `/workspaces/[workspaceId]` render the same surfaces as `/chat` and `/fusion`, whose cookie-auth inference reads the active-workspace cookie, so their capabilities (`COOKIE_WORKSPACE_CAPABILITIES`) stay with the cookie-workspace guard wherever they are mounted — the same workspace their in-surface gates and sidebar rows consult. In-surface gates on those pages follow the same rule through `useWorkspaceCapabilityForWorkspace` (ENT-2017). `/workspaces` and `/workspaces/new` are exact keys above the param segment and stay with the cookie-workspace guard.
- **Workspace-scoped vs account-scoped surfaces.** Outside `/workspaces/[workspaceId]`, the gates answer "does the *cookie workspace's* mode allow X". Account-scoped surfaces (e.g. management keys) need an account-level mode decision first — do not pretend the active workspace is the authority there; extend the table with an account-mode deriver instead.

## Governance

The completeness tests make it impossible to add a route or endpoint without editing a classification file, so **CI forces the touch**. Nothing currently forces the human: `@OpenRouterTeam/enterprise` was removed from `.github/CODEOWNERS` because those CI-forced touch points auto-requested the team on nearly every route or endpoint PR, drowning real review requests. Reviewers of classification changes are picked by hand until a narrower set of owned paths replaces the removed entries. `projects/web/REVIEW.md` additionally directs review tooling to flag unclassified new affordances, hidden-instead-of-disabled nav entries, and hand-rolled per-surface disabled treatments.

What this system deliberately does not cover: purely client-side leaf controls that neither navigate nor call the server. Once the action chokepoints in Enforcement status are complete, that residue cannot move data; keep an eye on client-only features acting on locally stored history.

## Enforcement status

Honest accounting of what enforces versus what is scaffolding awaiting its first consumer — keep this section current as the gaps close.

- **Live (client side):** the capability gates on the chat/fusion surfaces, the model-page playground, the nav treatment, and both layout guards with their default-deny for unclassified routes — including the Classifiers and Files pages under `/workspaces/[workspaceId]`, which are route-blocked in HIPAA workspaces. These are UX-grade: a determined user can bypass any client gate; the server-side bullets below are the boundary.
- **Live (server side, active workspace):** `requireWorkspaceCapability` is mounted on the Chatroom-gated `container-files` route app and the Files-gated `playground-files` route app. The completeness suite's linkage test forces the middleware onto every capability-classified mount, so the boundary widens mechanically as more endpoint classifications flip from `AVAILABLE_IN_ALL_MODES`.
- **Leaf-affordance capabilities (ENT-2141):** `broadcast_destinations` and `provider_api_keys` gate the *add* affordance on the observability and BYOK pages, checked in-surface against the viewed workspace row via `useWorkspaceCapabilityForWorkspace`. Their pages stay `AVAILABLE_IN_ALL_MODES` so existing destinations and keys remain visible and removable in a restricted workspace; the writes that add or exercise them are target-workspace gated per route on both the web-app API (`cfw-frontend-api`) and the management API (`cfw-public-api`, next bullets), so the configuration cannot be written past the client gate either. The router refuses the data movement itself as defence in depth — the broadcast fan-out is refused for HIPAA traffic (`packages/routing/helpers/check-hipaa-broadcast.ts`, applied by `findBroadcastWorkspaceId`), and BYOK rows and BYOK copies are never HIPAA-eligible (`packages/routing/filters/by-hipaa-eligibility.ts`). Broadcast is off wholesale in a HIPAA workspace: the enable transition (`enableWorkspaceHipaa`) clears `workspaces.is_broadcast_enabled` and sets `enabled: false` on every live `broadcast_destinations` row of the workspace in the same transaction (mirroring the clear onto `users.is_broadcast_enabled` for the entity's default workspace), and the toggle's enable direction (`POST /observability/broadcast` with `isBroadcastEnabled: true`, `POST /users/current` with `is_broadcast_enabled: true` for the default workspace, and on the management API `PATCH /api/v1/workspaces/{id}` with `is_observability_broadcast_enabled: true`) is gated under `broadcast_destinations` so the stored state and the API agree; disabling stays open. A workspace born HIPAA refuses `is_broadcast_enabled: true` at create time alongside prompt storage and data-discount sharing (`hasNewWorkspaceHipaaPrivacyConflict`). Deliberately open: the connection-test probe for a saved destination (an auth/connectivity check that carries no workspace content), metadata edits of existing keys, and OAuth provider subscriptions, the last pending OQ-5 (ENT-2015).
- **Live (server side, target workspace):** per-route gates on the writes that add or exercise a surface, recorded as `gatedPerRoute(...)`: classifier create/update/enable and on-demand runs (`Classifiers`), workspace file `prepare-upload`/`upload` (`Files`), enabling the auto-router plugin (`AutoRouter`), enabling prompt storage on `observability` and `users` (`PromptStorage`), enabling data-discount sharing on `workspace-settings` (`DataDiscountSharing`), the workspace broadcast switch's enable direction on `observability` and `users` (the account-level `is_broadcast_enabled`, which mirrors onto the default workspace), broadcast destination create/enable, copy-into, unsaved-destination connection test and test-trace sends on `observability` (`BroadcastDestinations`), and provider-key create/rotate and copy-into on `provider-api-keys` (`ProviderApiKeys`). All run through the shared helper, so their 403s carry the code (the pre-existing prompt-storage (observability, users) and data-discount (workspace-settings) gates alongside their original messages). The per-route linkage test forces a capability reference into every such route module. Custom content filters land next in the ENT-2144 stack.
- **Live (server side, management API):** `cfw-public-api` gates the same writes under API-key auth through the same helper (ENT-2148): destination create and an update that sets `enabled: true` (`routes/observability/destinations/create-destination.ts`, `update-destination.ts`, `BroadcastDestinations`), the workspace broadcast switch's enable direction on `PATCH /api/v1/workspaces/{id}` (`routes/workspaces/update-workspace.ts`, `BroadcastDestinations`, alongside its prompt-storage and data-discount switches), and credential create and raw-key rotation (`routes/byok/create-byok-key.ts`, `update-byok-key.ts`, `ProviderApiKeys`). The create routes always load the target workspace row (`src/helpers/resolve-gated-write-workspace.ts`), whether `workspace_id` was explicit or resolved from the default, so a HIPAA default workspace refuses too; the update routes resolve the workspace from the stored row. An entity-wide credential (`workspace_id` null) is visible to every workspace of the entity (`getProviderKeys` returns those rows alongside a workspace's own, and `labs/firecrawl-tos` still mints them), so its rotation is judged against all of them: `routes/byok/entity-wide-key-rotation-gate.ts` lists the entity's active workspaces and refuses under `ProviderApiKeys` when any is HIPAA-enabled, logging the first HIPAA workspace found as the `workspace_id`. This is stricter than the web-app API, whose `provider-api-keys` upsert (`services/cfw-frontend-api/src/routes/byok/provider-api-keys/upsert-handler.ts`, `authorizeUpsert`) judges the rotation of the same entity-wide key only against the workspace the caller resolved into, so a rotation the management API refuses for a HIPAA-holding entity is still reachable through the web app from one of its standard workspaces; aligning the two is a known follow-up. Reads, deletes, metadata edits, `enabled: false`, and an update that omits `enabled` stay open. Refusals are emitted through `src/helpers/workspace-capability-refusal.ts`, which keeps `error.metadata` on the wire; the plain `forbidden403Err` would drop it. There is no endpoint registry or linkage test for this worker, so a new public-api write on a gated surface must adopt the gate by hand and be reviewed for it.
- **Enable-time serialization:** the Presidio precondition (`listGuardrailsWithPresidioBuiltinsForWorkspace`, ENT-2127) runs in the enable handler before the write, outside any lock. `enableWorkspaceHipaa` repeats it inside its transaction after reading the owner's `users` row `FOR SHARE`, and every shipped guardrail-management writer that can bring a Presidio-backed guardrail to govern a workspace — guardrail create and edit, key and member assignment, key moves — holds that row `FOR UPDATE` for its whole transaction (`lockGuardrailOwnerInTransaction`; the one `api_keys.workspace_id` writer outside it is the intern provisioner's one-time legacy key re-home, `moveOrphanApiKeyToWorkspace` in `services/cfw-intern-provisioner`), so a Presidio write that committed just before the enable reached the lock is seen and the enable is refused with the `hipaa_enable_presidio_filters_present` invariant code (`packages/db/workspaces/hipaa-enable-constants.ts`), which the handler maps to the same typed 409 as the precondition (or to a plain retry 409 when the guardrail is gone again by its re-read). That closes the writer-first ordering only: a Presidio write that queues behind the enable runs once the flag is committed and is the application write gate's to refuse against the now-HIPAA workspace, and rows that predate the flag (BYOK keys, classifiers, auto-router settings) are not swept — the router remains their boundary (`packages/routing/filters/by-hipaa-eligibility.ts`, `packages/routing/helpers/check-hipaa-broadcast.ts`). An `api_keys` row with no workspace resolves to the entity's default workspace exactly as at inference (`packages/db/auth/get-user-by-key.ts` `withResolvedWsId`), so both reads count its Presidio assignments against that default workspace and no other.
- **Capability checks without the code:** two exist. The free-text guard on `generations-feedback` (`routes/generations-feedback/submit-generation-feedback.ts`) checks `FreeTextFeedback` on the active workspace but answers a 400 rather than a capability 403, because the client falls back to a category-only submission instead of treating the surface as blocked; the mount is classified `AVAILABLE_IN_ALL_MODES` for that reason. The Presidio-backed content-filter refusal (`NlpSensitiveInfoFilters`, ENT-2127) is a capability 403 that carries no `metadata` at all: `checkGuardrailBuiltinsHipaaAllowed` in `packages/guardrails/helpers/hipaa-presidio-boundary.ts` builds a plain `makeErrorT` with its own message and no code, and it is emitted from three `cfw-public-api` guardrail routes (`routes/guardrails/create-guardrail.ts`, `routes/guardrails/update-guardrail.ts`, `routes/guardrails/assignments/assert-legacy-guardrail-assignable-to-keys.ts`) and from `cfw-frontend-api` through `routes/guardrails/assert-guardrail-builtins-hipaa-allowed.ts`. That refusal predates the ENT-2148 gates and is not changed by them; converting it to the shared helper is open work. The public API's prompt-storage and data-discount gates on `services/cfw-public-api/src/routes/workspaces/update-workspace.ts` now build their 403s from the shared helper, keeping their original messages through the `message` override.
- **Not yet covered:** the inference data plane in `cfw-api` (cookie-auth and API-key paths) has no capability check here — server-side HIPAA handling of inference belongs to the backend isolation workstream (the `cfw-api-hipaa` dispatch work), which must land before any production workspace has `is_hipaa_enabled` set. Until then, chat/fusion restriction is client-side only.
- **Governance gap:** no code-owner rule covers the classification files, so a new surface can be classified and merged without an enterprise-team review. Closing this needs both a narrower CODEOWNERS entry set and the repo's required-code-owner-review setting enabled on `main`; CODEOWNERS entries alone only auto-request reviewers.
